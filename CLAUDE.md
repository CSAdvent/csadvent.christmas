# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical Rules

**These rules override all other instructions:**

1. **NEVER commit directly to main** - Always create a feature branch and submit a pull request
2. **Conventional commits** - Format: `type(scope): description`
3. **GitHub Issues for TODOs** - Use `gh` CLI to manage issues, no local TODO files. Use conventional commit format for issue titles
4. **Pull Request titles** - Use conventional commit format (same as commits)
5. **Branch naming** - Use format: `type/scope/short-description` (e.g., `feat/calendar/countdown`)
6. **Working an issue** - Always create a new branch from an updated main branch
7. **Check branch status before pushing** - Verify the remote tracking branch still exists. If a PR was merged/deleted, create a new branch from main instead
8. **Write tests** - All new/refactored code requires tests where applicable
9. **Run validation before commits** - Run `dotnet build` and `dotnet test` and verify no errors before committing
10. **No co-authors** - Do not add co-author information on commits or pull requests
11. **No "generated by" statements** - Do not add generated-by statements on pull requests

## Project Overview

- **The yearly cycle** is in `docs/runbook.md`. Keep it current when a change affects what organizers do, or when something happens, during the season.
- **Deploying**, and the one-time Azure, GitHub and credential setup behind it, is in `docs/deployment.md`. The README stays a short introduction: what the site does, how to run and test it, and links to these.

The new C# Advent site (csadvent.christmas), replacing the legacy site Matt Groves built. The pinned tracker issue (#52) lists every piece of work. The legacy code is a feature spec only; nothing is ported from it directly.

- **.NET 11** Blazor Web App (RC with a go-live license until GA in November 2026)
- **PostgreSQL** holds every season, archives included. Archive pages render from the database, never from static pages.

## Architecture

| Project | Role |
|---|---|
| `src/CSAdvent.AppHost` | Aspire app model |
| `src/CSAdvent.ServiceDefaults` | OpenTelemetry, health checks, resilience, service discovery |
| `src/CSAdvent.Web` | Blazor Web App; `Data/AdventDbContext.cs` and `Data/Migrations` |
| `tests/CSAdvent.UnitTests` | xUnit v3 on Microsoft.Testing.Platform; no database or containers |
| `tests/CSAdvent.IntegrationTests` | Starts the AppHost via `Aspire.Hosting.Testing`; web and database tests |

- **Package versions** are central in `Directory.Packages.props`. Target framework, nullable, and warnings-as-errors are in `Directory.Build.props`.
- **Render modes:** every page renders statically on the server, with **no interactive render mode and no Blazor script** (`blazor.web.js`, #185). Every form is a static SSR `EditForm` or a plain form posting to a minimal API, so a link or a form post is an ordinary whole page load. `App.razor` loads only `js/copy.js` and `js/countdown.js`, both written for whole page loads. Bringing the Blazor script back would bring back enhanced navigation (which fetched each `/go` link twice, #150), and an interactive render mode would put an antiforgery token on every page (#186) and needs `SeasonAccess` rethought, since a circuit has no request.
- **Migrations** run through Aspire's EF Core migrations integration (`AddEFMigrations` with `RunDatabaseUpdateOnStart`), never at app startup. Publishing produces a migration bundle, which every deploy runs before it updates the web app (Hosting, below).

## Styling

- **Tailwind CSS 4**, built by `build/Tailwind.targets` during `dotnet build`. It downloads the official standalone CLI into `.tools/` (gitignored, checked against a pinned SHA-256) and turns `src/CSAdvent.Web/Styles/app.css` into `wwwroot/app.css` (gitignored and generated, so never edit it).
- Tailwind only scans `src/CSAdvent.Web/Components`, and `wwwroot/js` for the classes the scripts add (`@source` in `Styles/app.css`). Write class names out in full in the Razor markup, because classes assembled from strings at runtime are never generated.
- Brand colors are the `advent-*` scale in `@theme`: `advent-600` (`#1a509d`) is the logo blue and `advent-400` (`#4e88c5`) the snowflake. Don't put `advent-400` behind body text, because its contrast on white is too low.
- Photos live in `wwwroot/images` as WebP with a JPEG fallback, in `<picture>` elements with `@Assets` URLs, which are fingerprinted so browsers keep them (#186): the candles fixed behind every page (`App.razor`, 1280 or 2560 wide by `srcset`) and the snowflakes behind the header (`MainLayout`). Don't use `url()` in `app.css` for images, because those addresses aren't fingerprinted. The header logo is `images/csadvent-logo-128.png`; emails keep `csadvent-logo.png`.
- Pages render statically on the server. `CalendarGrid` renders a season's days for the home page and the archive. `CalendarEntry` never carries a post's title or link before its reveal. A revealed entry with a URL but no title is "No post" (`CalendarEntry.HasPost` needs both), as its page is a 404.
- **Countdown (#31):** the day revealed next counts down ("Revealed in 11:42:07") once it's within 24 hours (`SeasonCalendar.CountingDownTo`, from `GeneratedAt`). `wwwroot/js/countdown.js` ticks it, correcting the visitor's clock with the server's time (`data-now`), and reloads once at the reveal, a few seconds late and spread out, if the countdown is still on the page (#156). A page with a countdown is `no-cache, no-store` (`CalendarGrid`), because a copy the browser kept would count down from an old `data-now`. It follows the rehearsal in the test season. Under it, "At midnight Eastern", to which `countdown.js` adds the visitor's own time ("(Thursday 9:00 PM your time)", from `data-reveal-local`) unless their clock says the same (#176).
- **Home page** (`HomeService.Plan`): a season's calendar is shown from when its sign-ups open (or December 1, if that's sooner or sign-ups aren't scheduled) **until the end of December** (`AdventSchedule.IsCalendarShown`), earliest season first, so creating next year's season early never replaces this year's. Once every day is revealed, `CurrentSeason` says "That's a wrap" instead of counting spots. While a day is today, `CurrentSeason` has **Jump to today** (to `#december-N`, #176).
- **Your spots on the calendar** (#175): for a signed-in contributor, the home page marks their spots ("Your spot", to My spots) and their pending requests ("You've requested this spot", instead of the claim link), through `SeasonCalendar.Marks` (`MySpotsService.GetCalendarMarksAsync`: two small queries, only when someone's signed in). Pages are `private`, so a marked page is only ever theirs, and the marks say nothing about a post before its reveal.
- **Between seasons** the home page is `OffSeason`, and it leads with the **next season** (#200): "C# Advent 2027" (the season that exists, or the one after the last), a one-line explanation, when its sign-ups open (if it's scheduled), its add-to-calendar files, **How to take part** (three steps, the backup list, About and the terms), and the announcements box (`SubscribeBox`, passed in as `Subscribe`). From **September 1** (`HomeService.CountdownFrom`) it counts down the days ("33 days until sign-ups open!"). Below that, **thanks for the latest finished season** (posts and authors) with the organizers' `between-seasons` content block, linking its archive and, once published, its retrospective (`FinishedSeason.HasRetrospective`); then **Wrote for C# Advent before?**, which signs past authors in to My spots for their history (`OffSeason.SignInToMySpots`), or links it once they're signed in; then the feeds. It's server-rendered, so there's no script.
- **Add to calendar** (#207, `CalendarFileService`, `CalendarFileEndpoints`): `/calendar/{year}/sign-ups.ics` (at `seasons.claims_open_at`, 404 until it's scheduled) and `/calendar/{year}/starts.ics` (the first reveal, from `AdventSchedule`), one-hour events written by `ICalendar`: CRLF lines folded at 75 octets, escaped text, times in UTC, and a stable `UID` (`csadvent-{year}-sign-ups@{host}`) with `DTSTAMP`. `OffSeason` links the next season's, and `/announcements` links the next season that hasn't started (`GetUpcomingAsync`; sign-ups only while they're still to come). Never the test season (404).
- Organizer pages work on the **current season** (`SeasonAdminService.GetCurrentYearAsync`): the earliest season that isn't finished (`AdventSchedule.IsFinished`). **When every season is finished there's no current season**, and Requests, Entries, Backups, Social and Other Advents show `NoCurrentSeason` rather than last year's data. Past seasons are opened from the overview's **Past seasons** list (`?year=`), where `PastSeasonNotice` says they're history. A finished season's sign-ups can't be edited.
- Component tests use **bUnit** (`BunitContext`) in `tests/CSAdvent.UnitTests`. `CalendarFixtures` builds a season as seen on a given date with a fake clock.
- **Accessibility and phones** (#169): `MainLayout` starts with a skip link to `#main`. Text is `slate-500` or darker (400 is too faint on white), and a long word wraps rather than running off a 320px screen (`wrap-break-word` on `body`). **A link to `#id` needs the page's own address** (`Navigation.ToBaseRelativePath(Navigation.Uri)`), because links resolve against `<base href>`, so a bare `#id` goes to the home page.
- **Form errors:** the `ValidationSummary` sits in a `<div role="alert">`, hidden while the summary has no `li` (.NET 11 renders a hidden placeholder for it, and for each field's message), and each field has its own `ValidationMessage` in `<div id="{field}-error">`, which the input names in `aria-describedby` with its help text (`{field}-help`), as on the claim form, My spots and the profile. Invalid fields keep a focus ring of their own (`app.css`). Copy buttons (`copy.js`) say "Copied!" to screen readers too, in a status region, and select the text if the clipboard refuses.

## Sign-in

- **Cookie sessions, with GitHub OAuth** through ASP.NET Core's built-in `AddOAuth` (`Auth/AccountEndpoints.cs`), not a third-party provider, with **PKCE** (`UsePkce`, #192: GitHub has accepted it for OAuth apps since July 2025, S256 only, and still wants the client secret too). Signing in calls `/user/emails` and keeps only a **primary, verified** address, then upserts the contributor by GitHub user ID (`ContributorSignIn`).
- **How long a sign-in lasts** (`Auth/AccountSessions.cs`, #192): 14 days after the last visit (sliding), except **organizers: 12 hours from signing in, never renewed** (`OnSigningIn` sets the expiry and `AllowRefresh = false`). `OnValidatePrincipal` signs out an organizer whose cookie isn't an organizer's (made one while signed in, or signed in before #192), so they sign in again and get one.
- **Every cookie is Secure outside Development** (`CookieSecurity`): the sign-in cookie, the antiforgery cookie and the test mode cookie, whatever the request looked like. Development follows the request, because the integration tests and the `http` profile are plain HTTP, where a Secure cookie never comes back. GitHub's correlation cookie is always Secure (ASP.NET Core's default).
- **Claims:** GitHub user ID (`NameIdentifier`), login (`Name`), verified email, the GitHub profile name (`csadvent:github_name`, if set) and `csadvent:contributor_id`. Use `User.GetContributorId()` to scope a contributor to their own data, and `User.GetDisplayName()` for the profile name with the login as a fallback.
- **Organizers** are GitHub user IDs in `Accounts:Admins`: CalvinAllen (`41448698`) and mgroves (`103484`). Use the `AdventPolicies.Admin` policy (for example `@attribute [Authorize(Policy = AdventPolicies.Admin)]`), which is checked on every request.
- **Dev sign-in** (`/dev/signin?login=...&id=...`) is mapped only when the environment is Development **and** `Accounts:DevSignIn` is true, which the AppHost sets in run mode. The integration tests use it, with organizer `9001` set by the AppHost in the Testing environment. The real GitHub handshake is tested by `GitHubSignInTests` (#199): `AddAccounts` and `MapAccounts` in a small host of its own, configured as in production, with GitHub played by a fake behind the OAuth backchannel and `GitHubUsers`.
- **GitHub settings** come from the AppHost parameters `github-client-id` and `github-client-secret`. They're optional locally and required in production; the app fails to start without them outside Development.

## Claims

- `/claim/{year}/{day}/{part}` (`CalendarLinks.Claim`) requires sign-in. `ClaimService.CheckAvailability` decides whether a slot can be requested: claims are open, the day isn't revealed, and nobody has claimed it. It's checked again on submit.
- A request is stored as `Pending` with the contributor's **verified GitHub email** (there's no typed-in email). Requests don't reserve the slot; the organizer approves one. A duplicate pending request from the same contributor is reported as already requested (the unique index catches two at once).
- **Limits** (#137, `ClaimOptions`): every request emails the contributor and the organizers, so one person can have at most `Claims:MaxPendingPerSeason` (3) requests waiting in a season, and make `Claims:MaxPerHour` (5) an hour whatever happened to them. The claim page says so instead of showing the form.
- **Social accounts** (Bluesky, Mastodon, LinkedIn, Facebook, Reddit, X) are optional fields on the claim form. They're saved on `contributors` with the name and link (`display_name`, `website_url`), so they're on the contributor's profile and prefilled next time, used to tag people in social posts (#59), and linked from their author and entry pages. `SocialAccounts.TryNormalize` accepts handles or profile URLs and stores one form per platform.
- **The name link is a website or blog.** Every form a contributor fills in (claim, profile, My spots, backup sign-up and offer) refuses social media profiles there (`[NotSocialProfile]`, `SocialAccounts.IsSocialProfile`: the big networks by host, and any `https://{server}/@user` as Mastodon, except Medium, Substack and YouTube). Organizer forms don't check it, because archive posts keep the links they were published with, Twitter included.
- **Without a website, the name links to the author's GitHub profile** (`AuthorLinks.ForName`, from the slot's contributor), on the calendar, the archive and the entry page. Calendar queries include `Slot.Contributor` for this.
  - **Where they signed up isn't a website** (#166): early seasons often linked an author's sign-up tweet (`/status/`) or comment on the sign-up post (`#comment-`). `AuthorLinks.Website` treats those as no website everywhere one is shown or used (the name link, entry and author pages, the profile's prefilled link), and they're gone from the archive JSON.
- **Statuses:** `Pending`, then `Approved` or `Declined` by an organizer, or `Withdrawn` by the contributor from My spots (nobody's emailed). Requests archived before #143 became `Declined`.
- New requests, approvals and declines go to `IClaimNotifier` (`EmailClaimNotifier`). It emails the contributor, and for new requests the organizers too, with replies going to the contributor. A failed send is logged without personal details and never blocks the claim.
  - **Approved into another spot** than the one asked for, the email says so (`ClaimEmailDetails.AskedFor`), and to reply if it doesn't suit them.
  - **Declined** (`ClaimEmails.Declined`, transactional, `ClaimDeclineReason` from the spot): it has gone to another author, with a link to the open days, or to the backup list once every unrevealed spot is taken; or, while it's still open, just that it wasn't approved.
- Blazor SSR forms: `[SupplyParameterFromForm(FormName = ...)]` on a nullable model, `Form ??= new()` to tell a GET from a POST, and `@bind-Value="Form!.Field"`. The posted field names are `Form.Field`.

## My Spots

- `/my-spots` (`MySpotsService`) is where contributors manage their own spots in seasons that aren't finished (until the end of December 25, so the last day's authors can add their posts on their day): add their post's title and URL (**the only way posts get onto the calendar**; nobody sends details by replying to an email), fix their name and link, and see pending requests. A pending request can be **withdrawn** (a plain form to `/my-spots/requests/withdraw`, `ClaimService.WithdrawAsync`, guarded by `xmin`), and says so when its spot has gone to someone else.
- A spot is theirs if `slots.contributor_id` is them, or if it isn't linked to anyone and its contact email is their verified GitHub email (spots an organizer added by hand). Saving links it. Anyone else's spot is a 404.
- The title and URL go together, because the calendar links the title to the post. Edits post the spot's `xmin` version back, so an organizer's edit in between isn't overwritten.
- **Once a post is revealed** (#155, `MySpotsService.SaveAsync`), every link we've shared goes to it, so:
  - **a new link waits for an organizer**: it's a post link request (`PostLinkService.RequestNewLinkAsync`, below), checked first (`CheckRequesterAsync`), so nothing is saved if they already have one waiting, have asked too often, or have no verified email. The spot's page shows the waiting link.
  - **a new title or summary shows straight away**, and the organizers get `SpotEmails.PostChanged` with what it was, to put back in the entry editor if needed. Social posts can't make links or mentions from it anyway (Social Announcements).
  - a revealed post can't be emptied there (`PostRequired`; they can drop out), and a spot that never got a post can't get one once its day is over.
  - The test season saves straight away, since nothing in it is published.
- **Dropping out** (until the day is over) clears the author, link, post, contributor and contact, so they're never named, sets `slots.dropped_out_at`, and emails the organizers. An organizer releasing a spot in the entry editor sets `dropped_out_at` too. A dropped-out spot that's still open is what the backup posters get asked about (#36).
- Emails link to `ClaimEmails.MySpots(site)`.
- **What's due** (#175): each spot lists the deadlines still to come (`SpotDeadlineList`, from `MySpotsService.DeadlinesOf`): its link by `Backups:AskFrom` the evening before (then before the reveal, then now), the blurb check from `Blurbs:CheckFrom` before the reveal, the reveal, and the announcement, which is the blurb's deadline. The suggested blurb comes after the spots, one format at a time (`SuggestedBlurbBox`: radio buttons and `group-has-[…]` classes, no script).
- **Backup posters on My spots:** the asks they can still answer (linking to each offer's page), their place on the list, or a link to join it (`BackupListService.GetMineAsync`), for the seasons of their spots, requests and backup lists, and the current season.
- **History:** My spots also lists every post linked to the contributor (`slots.contributor_id`) in finished seasons, as "Your C# Advent history" (`MySpotsService.GetHistoryAsync`). Organizers see "Returning · N posts" on that person's requests.
- **Asking for older posts** (#120, `PostClaimService`, `post_claim_requests`): a signed-in contributor can ask for a finished season's post that isn't on anyone's account to be added to theirs, at `/my-spots/claim/{year}/{day}/{part}` (`PostClaimLinks.Claim`).
  - **Finding them:** My spots has **Wrote for C# Advent before?**: a search by author name (`?find=`, `ILIKE` with `EscapeLike`, up to 50, prefilled with their name), plus their requests still waiting. An archive author's page (`/authors/name/{key}`, whose posts are on nobody's account) asks "Are you {name}?" and links that search with their name (`PostClaimLinks.Find`). Entry pages asked ("Did you write this post?") until readers started going straight to the post.
  - **Asking:** they tick "I wrote this post" and can add a note. Every request emails the organizers (`PostClaimEmails.NewRequest`, replies to the requester). It needs a verified GitHub email, is limited to `MaxPerHour` (10) per person, and one pending request per person and post (a filtered unique index). Never the test season, and never a season that isn't over.
  - **Reviewing:** organizers review at `/manage/authors/requests` (linked from Authors with the count) and `/manage/authors/requests/{id}`. Approving sets the slot's `contributor_id`, guarded by both rows' `xmin`, and can also link their other unlinked posts under the same name (`AuthorService.CombineAsync`). A post that's on someone else's account by then can't be approved. The requester is emailed either way (`Approved`, `Declined`).
  - **Already on someone's account:** the post can't be requested. The claim page, My spots and the privacy page say to email `Site:ContactEmail` if it's theirs.
  - **Retention:** requests keep no email address. A decided one is deleted 30 days later by `ContactRetention` (`PostClaimsKeptFor`), and the privacy page says so.
- **New links for older posts** (`PostLinkService`, `post_link_requests` with `post_link_changes`): for an author who moved their blog or a post. Posts in a season that isn't finished are edited on My spots instead, where a revealed post's new link is a request of the same kind (above), so one person's single pending request covers both.
  - **Asking:** `/my-spots/links` (`PostLinkLinks.Request`, linked under their history) lists every post on their account from finished seasons with its link in a field (`PostLinksForm`, `Form.Posts[i].Url` with a hidden `SlotId`). Whatever they change is **one request**, however many posts (`PostLinkService.Changes`: only their own posts, only links that differ), with an optional note. It emails the organizers once (`PostLinkEmails.NewRequest`, replies to the requester), needs a verified GitHub email, and is limited to `MaxPerHour` (5) per person.
  - **One at a time:** each person has at most one pending request (a filtered unique index). While it's waiting the page shows it with **Withdraw** (status `Withdrawn`), so they can fix a typo and ask again.
  - **Reviewing:** organizers review at `/manage/authors/link-changes` (linked from Authors with the count) and `/manage/authors/link-changes/{id}`, which shows each post's old and new link. **Approve** changes every link in the request (guarded by the request's `xmin`), and is refused if a post isn't on the requester's account any more; **Decline** changes nothing. The requester is emailed either way (`Approved`, `Declined`, transactional). Each change keeps the old link, so a bad approval can be undone in the entry editor.
  - **Organizers directly:** `/manage/authors/{id}/links` and `/manage/authors/unlinked/links?key=` (`AuthorPostLinks`, linked from both author pages) change an author's links without a request, any season, each guarded by its spot's `xmin`.
  - **Where it shows:** the calendar, the archive and every link we've published since 2026 go through `/go` or an entry page's redirect, so a new link applies to all of them at once. Links the old site published went straight to the post.
  - **Retention:** like post claims, no email address is kept, and a decided or withdrawn request is deleted 30 days later (`PostLinkRequestsKeptFor`).
- **Check my post** (#174, `BlurbSelfCheckService`, `PostBlurbCheck`): each spot with a post shows where it stands on the blurb, in the author's words, with a **Check my post** button (a plain form to `/my-spots/blurb-check`), and saving a new link on `/my-spots/{id}` checks it straight away (not a revealed post's, which waits for an organizer instead, #155). It's the worker's own check (`BlurbCheckService.CheckForAuthorAsync`) made whenever they ask, so before the reveal it's only information: no emails, no backups. A post that passed or that an organizer decided isn't checked again. Limits: `MaxPerHour` (10) checks per person, and `Blurbs:SelfChecksPerMonth` (2,000) that go to Claude in 30 days across everyone, so they can't use up the Anthropic spend limit ($25 a month). Each check is recorded in `blurb_self_checks` (who, which spot, when, whether it asked Claude), deleted after 31 days by `ContactRetention`.
- **How their posts did:** each revealed spot and history post shows its clicks (`PostTraffic`, from `entry_hits`, all time), and any visits to its entry page from before October 2026, labeled as such. Only the author sees their own; the public only sees a season's totals and its ten most-read posts in the retrospective.
- **Profile** (`/profile`, `ProfileService`, linked from the account menu): the name and link a contributor wants on the calendar, and their social accounts, with the same limits as the claim form (`ProfileForm`). It fills in their next claim, and a claim updates it. "Also show this on my spots" puts the name and link on every spot of theirs, past seasons included. Their GitHub login and verified email are shown read-only, because they come from GitHub.
- **Social accounts from GitHub:** on a contributor's first GitHub sign-in, `GitHubSignIn` calls `ProfileService.FillInFromGitHubOnceAsync`, which reads the social links on their public GitHub profile (`GitHubUsers.SocialAccountsAsync`) and fills in their **empty** account fields (`SocialAccounts.FromGitHub`: Mastodon by GitHub's provider, the rest by address, X on `x.com` or `twitter.com`; LinkedIn company pages are skipped). `contributors.github_social_checked_at` makes it once, so an account they remove doesn't come back; **Fill in from GitHub** on `/profile` runs it again on request. GitHub gets 5 seconds (`ProfileService.GitHubTimeout`), and if it fails the sign-in carries on and it's tried next time. Dev sign-in never calls GitHub, so the tests don't either.
- **Authors** (`/manage/authors`, `AuthorService`): every author in every season. Linked people are one row each, whatever names they've used; archive authors who aren't linked yet are grouped by name whatever its case or spacing (`AuthorService.Key`). Each season links to the post.
  - **Linking:** an organizer links an archive author to a GitHub login, which sets `contributor_id` on every finished-season post with that name. Someone who hasn't signed in gets a contributor record with only their public GitHub user ID and login, looked up through `GitHubUsers` (with the OAuth app's credentials, for GitHub's higher rate limit). Their first sign-in picks it up, because sign-in upserts by GitHub user ID. Posts from 2026 on are linked when their claim is approved. The privacy page says so.
  - **A linked author's page** (`/manage/authors/{contributorId}`, `AuthorEdit`) edits their profile (the same `ProfileService` as `/profile`), lists their spots with links to the entry editor, and has **Also wrote as**: add an unlinked archive author's posts to them (`CombineAsync`), with names sharing a word with theirs suggested first (`SharesAName`). **Unlink** (confirmed) only unlinks seasons that are over.
  - **An unlinked author's page** (`/manage/authors/unlinked?key=`) links them, or renames them on all their posts. Giving two unlinked authors the same name groups them together.

## Entry Pages and Traffic

- **Readers go straight to the post** (decided 2026-10-26, `EntryEndpoints.UseEntryRedirects`). Every revealed entry with a post (a title and a URL) has a page at `/{year}/day/{day}/{part}` (`EntryService`, `EntryLinks.Page`), and that address is still the link we publish, because platforms build their previews from it. But anyone else following it gets the same counted redirect as `/go` (`EntryEndpoints.ToThePostAsync`): one Click with its `?via=`, then a 302 to the entry's own `post_url`, with `Cache-Control: private, no-store` (the link can change) and `X-Robots-Tag: noindex`.
  - **People and crawlers alike:** search engines and unknown bots are redirected too (uncounted), so crawlers never see what readers don't, and they follow through to the author's post, which keeps the backlink.
  - **Who gets the page:** link previews (`EntryTraffic.LinkPreviewAgents`: Facebook, X, LinkedIn, Mastodon, Bluesky, Slack, Discord, Telegram, WhatsApp, Reddit, Iframely, Embedly, Teams and Skype), for its card and Open Graph tags, and signed-in organizers (`SeasonAccess.IsOrganizer`, the Admin policy's check), to see what's shared. Neither is counted, and the page counts nothing itself.
  - **How:** middleware after sign-in and ahead of the page (it matches the page's `ComponentTypeMetadata`), so a redirect costs one query and no render. Everything else is left to the page: before the reveal it says only when the post is coming (#5), a revealed spot without a post (or with no title) is a 404, and so is the test season for anyone who can't see it, link previews included.
  - **Our own links to entry pages** (author pages, search results, My spots, `/random`, and the page's previous, next and other-post links) now lead to the post too, as one untagged click. Nothing loops, because the redirect only ever goes to the post.
- **The page** (for link previews and organizers) shows the title, author, the author's links (`AuthorLinks.All`: website, GitHub, then the social accounts on their profile), a **Read the post** button and the day's other post.
- **Previous and next** (#205): a revealed entry's page links the season's revealed posts either side of it, in calendar order (`EntryService.Neighbors`, `rel="prev"` and `rel="next"`), with the reveal checked in C#, so the latest post has no next link until the next day is revealed.
- **A random post:** `/random` (linked from the archive) redirects to any post's page (and so on to the post), never cached, and robots stay out of it. It reads `RevealedPosts`: every post with a title, link and author whose reveal has passed (checked in C#, #5), from every season but the test season, even for its testers.
- **Summaries** (#208): an optional one-line `slots.post_summary` (up to `Slot.PostSummaryMaxLength`, 160 characters), set on My spots or in the entry editor and kept on one line by `PostSummaries.Clean`. Like the title, it's only shown once the post is revealed: under the title on the entry page and first in its meta description, first in the RSS item's description, in social posts where it fits, and on the Bluesky link card. Dropping out, releasing a spot, a backup taking it and resetting the test season clear it.
- **"Read the post" goes through `/go/{year}/{day}/{part}`**, which counts the click and redirects (302) to the entry's own post URL, like the entry page's own link. Nothing else can be a destination (but the post's saved copy once it's gone: Dead Links, below), so neither is an open redirect.
- **Every link we publish goes through us, tagged with `?via=`:**
  - Social posts and RSS link to the entry page (for the preview card), which sends readers on to the post.
  - The calendar (`via=calendar`) and the daily email (`via=email`) link straight to `/go`. The calendar's labels ("Post 1", or the day when there's one post a day) are plain text: they linked entry pages for search engines (#167), which would now just lead to the post like the title.
  - The entry page's button passes on the tag the visit arrived with (`site` if none).
  - Retrospectives link to their most-read posts' pages with `via=retrospective`.
  - Tags are normalized by `EntryVia` (unknown becomes `other`).
- **Counting:** `entry_hits` records a `Click` with the slot, time and tag, from an entry page's link or `/go`. Visits to entry pages (`View`) were counted until October 2026, when readers started going straight to the post: those are kept as history (My spots shows them as visits "until October 2026", and retrospectives keep the numbers they were generated with), and nothing records new ones. There's no IP, cookie or user agent, so nothing personal, and the hits are kept for the stats (#62). `EntryTraffic.IsPerson` skips link previews (`LinkPreviewAgents`, which are never counted), crawlers, scripts, prefetches and non-GET requests. Both links also skip Blazor's enhanced-navigation fetch (`EntryTraffic.IsClick`), which pages still open from before #150 may make before loading the link as a page. Until that fix (October 2026), each click from the site's own pages was counted twice. The organizers' entries list shows clicks per spot. A count that can't be saved is logged (an error, so the alerts hear about it) and never costs the reader the redirect (#196, `EntryService.RecordAsync`).
- **Preview tags:** `SocialMeta` puts Open Graph tags, `twitter:card` (large image), `twitter:site` (`Social:X`), a canonical URL without the query string, and `fediverse:creator` (`Social:Mastodon`) on every public page. A revealed entry's page adds `article:published_time` (its reveal), and no structured data, since search engines never get it (Search Engines, below).
- **Cards** (`CardRenderer`, SkiaSharp):
  - What they show: a revealed entry's page uses `/cards/{year}/{day}/{part}.jpg` (title, author, day). Season pages use `/cards/{year}.jpg`. The home page (`CardLinks.Home`) uses the season on the calendar, or between seasons the next season's card saying when its sign-ups open (`CardLinks.Upcoming`), and otherwise the general card: **never a finished season's**, which would read as if that Advent were still on. Anything else, including entries before their reveal, uses the static general card `images/social-card.jpg`.
  - Size: 1200×630 JPEGs of about 110 KB, under Bluesky's 1 MB limit.
  - Caching: `CardLinks` adds `?v=` (a hash of the text, or the post count), so an edited title gets a new URL. A card asked for by its current versioned link is `immutable` for a year; without a version, or with an old one, it's cached for a day (`CardEndpoints.CacheControlFor`). Rendered cards are kept in memory.
  - Before an entry's reveal there's no card for it (404).
  - Fonts and images: Inter Bold and Regular (SIL Open Font License, `Cards/Assets/Inter-LICENSE.txt`), the card background and the logo are embedded resources. Linux uses `SkiaSharp.NativeAssets.Linux.NoDependencies`, so containers need no fontconfig or system fonts. `CardRenderer.Printable` drops characters Inter can't draw (emoji, for example) rather than draw boxes.

## Dead Links

- **Older posts disappear** (#201: one in four 2017–2018 posts sampled was a 404), so `LinkCheckService` (`DeadLinks/`) checks that each post in a **finished** season (never the test season) is still at its address, and keeps the answer in `link_checks` (one row per slot, for the address it checked; a changed address starts again from scratch).
- **Slowly, on purpose** (`LinkCheckWorker`, a `PeriodicWorker` step every 15 minutes, `LinkCheckOptions`): at most `PostsPerRun` (2) posts a run, the most overdue first, one per site, and no site checked again within `HostPause` (an hour), so dev.to's two dozen posts take a day. That's at most 192 checks a day: a first pass over the archive's ~450 posts in 2–3 days, then about 15 a day. A post that loads is checked again in `RecheckAfter` (30 days, give or take 10%, so they don't come round together). It doesn't run when the app starts, so a deploy never sends a burst. Each run leases the rows it checks (`leased_until`, claimed with a conditional update), so replicas never check the same post.
- **What counts** (`LinkProbes`): `WebLinkProber` asks for the page with its own client (`PublicAddresses`, 20 seconds, no factory retries, our user agent) and reads only the status, never the body. A 404 or 410, a host that no longer exists, a 5xx, no answer, a bad certificate, endless redirects, or a post that now lands on a site's home page is a failure. A 401, 403, 429 or other 4xx (Medium turns checks away), and LinkedIn's non-standard 999 from any site (`LinkProbes.RequestDenied`), is **Refused**: no telling, so readers keep the post.
  - **Sites whose answers can't be trusted** (`LinkProbes.UntrustedHosts`, one list next to the rules, any subdomain): **linkedin.com**, which answers checks like ours with a 404, a 999 or a sign-in wall even when the post is up. Nothing from them is ever a failure, only Refused (a page that loads still counts as working), so a live post is never marked dead and its readers never sent to an old copy. Add a site only with evidence; an organizer's **It's gone** still works for them.
- **Dead after `FailuresBeforeDead` (3) failures in a row**, a day or more apart (`RetryAfter` times the failures: a day, then two), so an outage isn't a dead post (`LinkCheckRules`). A dead post that loads again is Working again; one whose site starts turning the check away stays dead.
- **Saved copies:** a dead post's archived copy is looked up with the Wayback Machine's availability API (`WaybackArchiveLookup`, own client, `PublicAddresses`): the snapshot closest to its reveal that loaded (status 200), only ever a `https://web.archive.org/web/…` address. At most `ArchiveLookupsPerRun` (2) a run, each claimed first. One with no copy is asked again after `ArchiveRecheckAfter` (30 days), and one the archive didn't answer for after 6 hours.
- **Readers get the copy** while the post is dead: every redirect to a post (`EntryEndpoints.ToThePostAsync`, shared by `/go` and entry links) asks `EntryService.DestinationAsync`, which only uses a copy kept for the spot's current address. A dead post without a copy still goes to its address. The entry page (for organizers and link previews) says so (`GonePostNotice`), and its button reads "Read the saved copy". Before the deploy's migrations add the table, everything goes to the post (`MissingSchema`).
- **Organizers** see dead, failing and turned-away posts at `/manage/authors/dead-links` (`DeadLinkList`, linked from Authors with the count and from the navigation), a **Dead link** badge on the entries list, and a **Dead-link check** panel on each revealed entry's page (`LinkCheckCard`). Plain forms to `/manage/links/*` (`LinkCheckEndpoints`, Admin policy, antiforgery checked by binding the form) come back with `?links={result}-{slotId}`: **Check now**, **It works** (a false alarm; stands until the link changes or someone checks), **It's gone** (a domain that's been sold, say; looks up a copy straight away), **Look up a saved copy**, a **Saved copy** of their own (any web address; empty clears it, and runs then never look one up), and a **New link** for an author who moved the post (guarded by the spot's `xmin`; every link we've published follows it at once).
- **The organizers are emailed, never alerted** (`DeadLinkEmail`, `dead-links-found`): a failed check is expected, so the prober logs it as information, and the errors alert leaves out the exception .NET's HTTP tracing records on the request's span (Hosting). Instead, a step of its own after each check (`LinkCheckWorker.DeadLinksEmail`) sends one email a day from `LinkChecks:EmailAt` (8 AM Eastern): every post found dead before then that the organizers haven't heard about, with its address, what the check found, and whether readers get a saved copy. One email rather than one per post, because the first pass over the archive finds dozens. Each post is claimed on `link_checks.organizers_emailed_at` before it's queued (undone if it can't be), which is cleared once it isn't dead or its check starts again, and set when an organizer marks it gone or checks it themselves.
- **Development and tests:** `LinkChecks:SamplePages` (Development) uses `SampleLinkProber`, which answers for `*.links.csadvent.test` by the first path segment (`working`, `refused`, `down`, `home`, anything else a 404) and calls every other address loaded without fetching it, and `SampleArchiveLookup` (a copy of any sample address with "archived" in it). `POST /dev/links/run?at=…&year=…` runs a pass, and `POST /dev/links/email?at=…&year=…` the email. The AppHost turns the worker off in the Testing environment (`LinkChecks:CheckInBackground`). `DeadLinkTests` use seasons 2680-2689.

- **C# Advent's own accounts** are in `Social` (`SocialAccountsOptions`):
  - Bluesky `csadvent.christmas`
  - Mastodon `@csadvent@mastodon.social`
  - the Facebook and LinkedIn Pages

  - X `@csadvent`

  The footer links them all ("Follow C# Advent"), with `rel="me"` on Mastodon so its profile can verify the site.

- **Every revealed entry with a post gets one announcement per platform:** Bluesky, Mastodon, LinkedIn, Facebook, Reddit and X, using `Claims.SocialPlatform`. The content is the same everywhere (`Announcement`: title, author, "C# Advent 2026, December 6, part 2", and a link to the entry page tagged with the platform: the platform's preview fetcher gets the page and our card, and readers go straight to the post). `AnnouncementFormatter` handles each platform's conventions:
  - **Bluesky:** 300 graphemes, `@handle` mentions, and a compose intent.
  - **Mastodon:** 500 characters, where a link counts as 23 and `@user@server` counts as `@user`. The share link opens on `Social:Mastodon`'s server.
  - **LinkedIn:** 3000 characters, a "tag the author" hint, and a composer link (`linkedin.com/feed/?shareActive=true&text=`). LinkedIn doesn't document it (its documented share link only takes a URL), so if the composer opens empty, paste with Copy.
  - **Facebook:** fewer hashtags, and a hint.
  - **Reddit:** a title of up to 300 characters plus the link, no hashtags, and a submit link.
  - **X:** 280, counted X's way (`XLength`): a link is 23, an emoji or "…" is 2, and text X would link, like "ASP.NET", counts as a link. `@username` mentions, and X's documented web intent (`x.com/intent/tweet?text=`).
  - **Long titles** are shortened with an ellipsis to fit.
  - **The author's words are inert** (#155): `AnnouncementFormatter.Inert` puts an invisible word joiner after each "@", hashtag "#", the ":" of "://" and each dot before a letter in the title, the author's name and the summary, so no platform makes a link, mention or hashtag from them (X and Facebook link anything that looks like a domain). Only our own parts go live: the entry link, the author's account and our hashtags.
  - **The post's summary** goes between the title line and the link where it fits with the whole title (`AnnouncementFormatter.Fit`), and is left out otherwise; never on Reddit, whose post is a title and a link.
- **`/manage/social`** (organizers) shows a day's announcements, today by default. Each has a preview, a count against the limit, Copy buttons (`wwwroot/js/copy.js`, `data-copy="element-id"`), and the composer link where one exists. Upcoming days are preview-only, with no composer and no marking before the reveal (#5). Each card has an id (`announcement-{slot}-{platform}-card`) that its buttons' return URL ends with, so Mark as posted, Undo and Retry come back to it (the endpoints add their result to the query ahead of the fragment, `ReturnUrl.WithQuery`, #170). **How each platform is posted** is below the posts (`#platforms`), linked from the top.
- **Mark as posted / Undo** are plain forms posting to `/manage/social/mark` and `/unmark` (minimal APIs; binding the form checks antiforgery; Admin policy). They're plain because the page has one per entry and platform, and Blazor form names must be unique. They record `social_posts` (unique per slot and platform: status, time, optional post link, and who marked it; `automation` for #61).
- **Automatic posting** (#61, `Social/Posting`): Mastodon, Bluesky, the Facebook Page and X. LinkedIn and Reddit have no API access, so they're always copy and paste.
  - **Modes:** each platform is Automatic, Manual (the default) or Off in `social_platform_settings`, set on `/manage/social` (plain forms to `/manage/social/mode`), so switching takes effect without a redeploy. Off platforms are left off the page. Automatic needs a publisher (`SocialPublishers.For`): credentials, or dry-run mode.
  - **When:** `SocialPostingWorker` runs `SocialPostingService.RunAsync` every 5 minutes. Each entry goes out on its day at `SocialPosting:PostAt` (10 AM for post 1, 2 PM for post 2, Eastern), or as soon as its link arrives (or its blurb check passes) after that, but never once its day has passed. **Never the test season.**
  - **Exactly once:** a run claims an announcement by inserting its `social_posts` row as `Posting` before posting; the unique index means only one run or replica gets it, and anything marked by hand is skipped. A failure is `Failed` with the platform's error, retried after 5, then 10 minutes, up to `SocialPosting:MaxAttempts` (3), then waits for **Retry now** (`/manage/social/retry`). Entry and season posts share the claiming, recording and recovery (`SocialPostAttempts`, over `ISocialPostRecord`, #187).
  - **May have gone out** (#154): once the request that makes the post has been sent, a timeout, a dropped connection or a 5xx can come after the platform posted it.
    - Every publisher sends that request with `SocialPostRequests.SendPostAsync`, which throws those as `SocialPublishException.MayHavePosted`. A 4xx, or a request that never left (DNS, connecting, TLS), is a plain failure, and a 2xx whose body can't be read still counts as posted.
    - Such a post is `Unconfirmed` (`SocialPostAttempts.StatusAfter`): never tried again by itself, shown in amber ("Did it go out?") with **Retry now** and **Mark as posted**, for an organizer to look at the account first. Only where trying again can't post twice (`ISocialPublisher.RetriesAreSafe`: Bluesky) is it just `Failed`, and retried.
    - Mastodon's `Idempotency-Key` only lasts an hour, and X doesn't document how recent a refused duplicate must be, so neither counts as safe.
    - A row of either kind still `Posting` after 15 minutes was interrupted, so it's `Unconfirmed` too (`SocialPostAttempts.GiveUpOnInterruptedAsync`). Both services' `RunAsync` look for them first, by the real clock and whatever the modes.
  - **Alerts** (#161, `SocialPostingAlerts`): the organizers are emailed whenever a post stops and waits for them. That's `Unconfirmed` (`social-post-unconfirmed`, interrupted posts included), or failing its last automatic try (`social-post-gave-up`; for the automatic "sign-ups are open" post, any failure, since season posts are never retried by themselves). Not for a try an organizer just made from the page, whose result they see. The run whose conditional update recorded it sends it, so replicas never both do.
  - **Publishers** (`ISocialPublisher`, tested with fake HTTP handlers): Mastodon `POST /api/v1/statuses`; Bluesky through XRPC with an app password, marking up only the entry link, the author's handle (`FormattedAnnouncement.Mention`) and `OurHashtags` as facets (UTF-8 byte offsets; mentions resolved to DIDs) and building the link card from our share card (`uploadBlob`); Facebook `POST /{page-id}/feed` with the Page token in the Authorization header; X `POST /2/tweets`, signed with OAuth 1.0a (`XPublisher.Authorization`, tested against X's worked example), with no idempotency key. X's API is paid per use. They share an `HttpClient` of their own (`SocialPublishers.CreateClient`), because the factory's default retries could post twice after a timeout.
    - **Bluesky's record key** is fixed per announcement (`BlueskyPublisher.RecordKey`: a TID made from the idempotency key, with a time in early 2026). Each try asks `com.atproto.repo.getRecord` first and returns the post it finds (a missing one is a 400 `RecordNotFound`), and `createRecord` with a taken key fails rather than posting twice, so its retries are safe.
  - **Credentials** are secrets: AppHost parameters `mastodon-access-token`, `bluesky-app-password`, `facebook-page-id`, `facebook-page-token`, and X's `x-api-key`, `x-api-key-secret`, `x-access-token` and `x-access-token-secret` (all four needed), added only when published **and** given a value (CI's `MASTODON_ACCESS_TOKEN`, `BLUESKY_APP_PASSWORD`, `FACEBOOK_PAGE_ID`, `FACEBOOK_PAGE_TOKEN`, `X_API_KEY`, `X_API_KEY_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_TOKEN_SECRET`), so a missing one never breaks a deploy and nothing run locally can post for real. **Check** on the page signs in with them and records the result. `SocialCredentialCheck` (from the worker) also checks each Automatic platform once a day from `SocialPosting:CheckAt` (8 AM Eastern), claiming the day's check on `social_platform_settings.checked_at` so replicas don't both run it (an organizer's check that day counts), and emails the organizers when one fails.
  - **Send a test post** (`/manage/social/test`, `SocialPostingService.SendTestAsync`) posts for real a test formatted exactly like an announcement but about no entry (`Announcement.Test`: "C# Advent test post (please ignore)", with the general card on Bluesky and a fresh idempotency key). It links to a page of its own, `/test-post/{id}` (`noindex`), because platforms cache a preview by canonical URL: the home page's was the old site's ("(archived)") on Facebook and mastodon.social, while real announcements link to new entry pages that nothing has cached. Nothing is marked posted. It records the test post's link and counts as a credential check.
  - **Season posts** (`/manage/social/signups`, `SeasonSocialService`, `season_social_posts`): **"sign-ups open soon"**, counting down ("in 8 days", `AnnouncementFormatter.FormatSignUpsSoon`), posted by hand whenever and as often as organizers like (Post now on automatic platforms, or copy and Mark as posted), and **"sign-ups are open"** (`FormatSignUpsOpen`), which Automatic platforms post by themselves at `Reminders:SendAt` (9 AM) on the day the current season's sign-ups open, once per platform (a unique index filtered to that kind), within 2 days of opening (`AdventSchedule.IsTimeToAnnounceSignUps`, shared with the announcements email), never for the test season. A season post that failed or is unconfirmed is never tried again by itself: **Post now** tries it again, and a "soon" one that didn't go out can be **Dismiss**ed. Their links go to the home page with `?via=…&season=…` (and `&in=` for the countdown): addresses never posted before, so Mastodon fetches a fresh preview rather than its cached one of the home page. Before sign-ups open, the "sign-ups are open" cards show their composer button disabled ("Opens once sign-ups open"). `POST /dev/social/signups/run?at=…&year=…` runs the automatic post.
  - **Dry run:** `SocialPosting:DryRun` (Development, so locally and in the tests) stands in for missing credentials and only logs. `POST /dev/social/run?at=…` runs a pass at any time; `SocialPostingTests` use it on a December 2025 day. The AppHost turns the worker off in the Testing environment (`SocialPosting:PostInBackground`).

## RSS

- **`/rss`** carries the latest 100 revealed entries and published retrospectives from every season (`RssFeed.LatestItems`, #194; it reads newest first and stops once it has them), and **`/archive/{year}/rss`** carries all of one season's (`RssFeed`, hand-written RSS 2.0 with `atom:link` and `dc:creator`). The channel image is the logo at 144 pixels, the widest RSS 2.0 allows (`images/csadvent-logo-144.png`, a stable path). Items are newest first by reveal time (posts in order within a day), and only revealed entries are included: the reveal is checked in C#, not SQL (#5). A retrospective is dated when it was published, with the GUID `csadvent-{year}-retrospective`.
- **Each item:**
  - `pubDate` is the reveal time.
  - The GUID is `csadvent-{year}-{day}-{part}` (`isPermaLink="false"`), so edits never duplicate an item.
  - The link goes to the entry page with `?via=rss`, never straight to the post, so following it is a counted click.
  - The description reads like "Day 6, post 2 of C# Advent 2025, by …", after the post's summary if it has one.
- **Caching:** responses carry an ETag (a hash of the XML) and `Cache-Control: public, max-age=600`, and a matching `If-None-Match` gets a 304.
- **Discovery:** every page has `<link rel="alternate">` for `/rss` in `App.razor`, and season pages add their own feed through `SocialMeta`'s child content.

## Search Engines

- **`/robots.txt` and `/sitemap.xml`** (`Content/SearchEndpoints.cs`, #38): robots keeps crawlers out of signed-in, organizer and personal pages, the `/random` redirect and the archive's search results (`SearchEndpoints.Disallowed`), and points at the sitemap. The sitemap lists the public pages, every finished season's archive and published retrospective, and every author's page, and never the test season. Not entry pages: they redirect crawlers to the post (below), and a sitemap lists pages, not redirects. Both are cached for an hour.
- **`/go` and entry pages are crawlable** (decided 2026-10-26, #167): crawlers follow them to the authors' posts, so authors keep the followable link the legacy site gave them, and both redirects send `X-Robots-Tag: noindex`, so they're never listed themselves (a disallowed URL can still be listed from links, with no content). Crawlers get the same redirect as readers, never the page, so there's no cloaking, and they aren't counted (`EntryTraffic.IsPerson`). Nothing on the site needs to link entry pages for search engines any more.
- **Titles:** the home page's is "C# Advent: two C# posts a day, December 1–25", and every other page's ends with "C# Advent" (the 404 is "Not found · C# Advent").
- **Structured data** (#195, schema.org JSON-LD from `StructuredData`, rendered by `JsonLd` in `SocialMeta`'s child content):
  - The home page has the `WebSite` (published by C# Advent, `sameAs` its accounts) and, as an `Event`, the season on the calendar or between seasons the next one.
  - Each finished season's archive page has its `Event`: online, from the first reveal to the end of December 25.
  - Entry pages have none. They had a `BlogPosting` until readers and crawlers started going straight to the post (October 2026): only link previews get the page now, and they read its Open Graph tags.
  - Never for the test season. The JSON is escaped so it can't close its script element, and JSON-LD isn't a script that runs, so the Content-Security-Policy (Hosting) doesn't apply to it.
- **No analytics** (decided 2026-10-23): the click counts are enough, and the privacy page promises no tracking.

## Caching and Compression

- **Pages** (`Content/PageCaching.cs`, #186): a page that sets no Cache-Control of its own is `private, no-cache` with a weak ETag (a hash of its HTML), so the browser can keep it but asks again first, and an unchanged page is a 304. Pages are rendered into memory for that, so don't use `[StreamRendering]` (there's no Blazor script to apply it anyway).
- **Antiforgery tokens are only on pages with a form**, which only works without an interactive render mode: Blazor then only issues a token when a form asks for one. Antiforgery makes those pages `no-cache, no-store` and sets its cookie. That's every page for a signed-in visitor (the sign-out form), and for anyone else the pages with the announcements box. A page with a countdown is `no-store` too (`CalendarGrid`).
- **Compression** (`Content/Compression.cs`, #164): Brotli or gzip for pages, both feeds, the sitemap and calendar files. Static files are compressed at build time and served that way by `MapStaticAssets`. **A signed-in visitor's pages aren't compressed** (`PageCompressionProvider.IsPersonal`), against BREACH: they carry personal details and the sign-out form's token. Anyone else's pages carry nothing secret: a form's token goes with a SameSite=Strict cookie that a request from another site doesn't send.
- **Static files** referenced with `@Assets[...]` are fingerprinted and cached for a year. Frame protection is `frame-ancestors 'self'` and `X-Frame-Options: SAMEORIGIN` on every response (`SecurityHeaders`, Hosting), since Blazor's own `frame-ancestors` went with the interactive render mode.

## Backup Posters

- **Joining:** anyone signed in with a verified GitHub email can join a season's backup list at `/backups/{year}` while sign-ups are open (`BackupListService`), including people with a spot. Anyone can read the page; it asks visitors to sign in with GitHub to join (#189), and a form posted without a sign-in goes to sign in. The list (`substitutes`) is in sign-up order, and organizers see it at `/manage/backups`.
- **The sign-up email goes once per person and season** (#137): leaving deletes their place on the list, so `backup_signup_emails` records it before it's sent (unique per season and contributor; a failed send removes it). Joining again finds the record (checked before inserting one, #157), says "You're back on the list" and sends nothing. The records go with the backup list on February 1, and with the test season's activity.
- **When a spot needs a backup** (`BackupService`):
  - `CouldUseBackup`: the spot was dropped (`dropped_out_at`, no author), it has an author but no post link, or its post's blurb check is Missing (`BlurbMissing`, see Blurb Check), and its day isn't over.
  - `NeedsBackup` adds the timing: dropped spots right away, missing links from `Backups:AskFrom` (6 PM) on the evening before, missing blurbs from the reveal (or as soon as an organizer chooses **Use a backup**).
- **Asking:** one backup at a time in sign-up order, each with `Backups:AnswerWithin` (4 hours) before the next is asked too (`Backups:AnswerWithinOnTheDay`, 1 hour, for a missing blurb). `ReminderWorker` runs `BackupService.RunAsync` every 15 minutes, a spot at a time: one that throws is logged and the rest carry on (`EachSpot`, #147). Dropping out (My spots), releasing a spot (entry editor) and blurb decisions call `OfferNowAsync`, so the first ask goes out immediately; if it fails, it's logged and the next run asks, so the author's or organizer's action never fails. A decline is picked up by the next run.
  - **Rounds** (#153, `BackupRound`, `backup_rounds`): everyone's asked once per round, and the organizers hear "nobody's left" once per round. A new round starts when the spot needs a backup for a new reason or a new author (`BackupRound.HolderOf`: the dropout's time for a dropped spot, else the author's contributor ID, or their name for an author added by hand), so a spot dropped in November that nobody took, then given to an author whose link is missing in December, asks everyone again. Rounds only go forward (`Number`, unique per slot); a round's offers are the spot's offers after its `offers_after` (the highest offer ID when it started), so `backup_offers` has no column for it. A new round withdraws the asks nobody answered, but a backup standing by stays on deck. On the offer page, a backup who took the spot before this ask (and dropped out too, say) doesn't count as someone else stepping in.
    - **The blurb check's deadline email counts only this round** (#234, `BackupService.HasBackupThisRoundAsync`): the backup standing by, whichever round they were asked in (there's one at most, and no new round starts while one stands by, so a backup who accepted for a missing link still stands by when the link arrives without the blurb), or one who took the spot in the round it's in now (`GetRoundAsync`, the latest round or the next one, unsaved). A backup who filled it in an earlier round, then dropped out or saw it given to someone new, doesn't count. `BlurbRoundTests` use seasons 2600-2602.
  - **Asks that don't arrive** (#149): an ask goes through the email queue with the offer's `ExpiresAt` as its deadline (`Reference` `backup-offer:{id}`). One that can't be queued deletes its offer, so the next run asks the same backup again. One the queue gives up on (Failed, or Expired unsent) ends that offer's time and asks the next backup straight away (`BackupAskUndelivered`, `BackupService.AskUndeliveredAsync`).
- **Accepting:** only the signed-in backup who was asked can accept, on `/backups/offers/{id}`, and anyone asked can accept while `CouldUseBackup` holds. A dropped spot is taken straight away. A missing link waits for the reveal (midnight): if the author's link arrives first, the offer is withdrawn and the backup is thanked. A missing blurb waits for its deadline (the announcement), or not at all after **Use a backup**; the backup's own post is checked when they accept, and refused without the blurb (`BackupOfferOutcome.MissingBlurb`).
  - **The organizers can keep the author** (#148): when the check (not an organizer) found the blurb missing, a backup standing by takes the spot only once the organizers have had `Backups:OrganizersNotice` (1 hour) since they were told, so never sooner than that after the deadline (`BackupService.IsDue`). The blurb check tells them (see Blurb Check), recorded in `sent_reminders` (`AdminBlurbBackupStandingBy`, whose time is when they heard). Only a notice sent since this backup accepted counts (#234): one about an earlier backup (from an earlier round, or one who left the list) doesn't, so this one waits for a notice of its own. An organizer's own decision, or the deadline's "no blurb and no backup" email, needs no notice.
- **Taking a spot** replaces the author, link, post, contributor and contact, clears `dropped_out_at`, and sets the substitute's `assigned_slot_id`. It emails the backup, the organizers and (for a missing link or blurb) the original author.
- **Guards:**
  - Each backup is asked about a spot once per round, and has one waiting ask per spot at most (`ix_backup_offers_one_ask`, unique `slot_id, substitute_id` on `Asked`), so two runs asking at once can't both send it.
  - Only one acceptance can be pending per spot (`ix_backup_offers_one_taker`, on `Accepted`).
  - The slot's `xmin` stops a spot from being used twice. The offers' `xmin` too: a run closing offers, or starting a round, while a backup answers saves nothing and tries next run, and accepting tries once more with the offer as it is now (`BackupOfferOutcome.Changed` if it changed again) (#147).
  - The organizers' "nobody's left" email is recorded once per round on `backup_rounds.nobody_left_at`, claimed with a conditional update (nothing inserted, #157) and cleared if the email can't be queued, so a later run tells them (#149). `sent_reminders`' `AdminBackupsExhausted` records are from before rounds.
- **Trying it:** `POST /dev/backups/run?at=…&year=…` (Development only) runs a pass at any time. `BackupTests` pass `year` so seasons don't affect each other, and keep in mind that pages run on the real clock (long before the test seasons). `BackgroundJobTests` (seasons 2560-2579) cover rounds and a spot that fails, made to fail by triggers only the test database gets.

## Blurb Check

- **The rule** (#128, `Blurbs/`): every post from 2026 on (`BlurbRules.AppliesTo`, the test season too) opens by saying it's part of that year's C# Advent calendar, with a link to csadvent.christmas. **The wording is the author's**; `SuggestedBlurb` is only a ready-to-paste example (text, Markdown, HTML) on My spots. Authors see the rule with that example before they request a day (on the claim page, next to the terms) and in the request-received email, and the approval email and terms explain it again.
- **Checking a post** (`BlurbChecker`, which saves nothing):
  - `WebPostFetcher` fetches it with its own client, like the logo fetcher: `PublicAddresses`, 15 seconds, 2 MB, no factory retries. Video sites can't be read, so they're Couldn't check.
  - `ArticleReader` (AngleSharp) reads the opening: the article without its site, `nav`, `aside`, `footer`, scripts or forms, up to `Blurbs:OpeningCharacters` (2,000) visible characters, with links as `[words](url)`. A blurb in the post's footer isn't at the top.
  - **No link back** in the opening (`BlurbRules.IsLinkBack`) is Missing without asking Claude, but only on a page that's clearly the post: its calendar title is in the page's opening, `title`, `og:title` or top heading, whatever the case or punctuation (`BlurbChecker.LooksLikeThePost`, `PostOpening.Titles`). Otherwise it's NeedsDecision (`BlurbChecker.NotThePost`, #148): pages that need JavaScript (Blazor WebAssembly blogs), sign-in, cookie and bot walls, and "not found" pages that answer 200 all look like that.
  - **Otherwise Claude Haiku 5.5** (`HaikuJudge`, Anthropic's `AnthropicClient` with `Blurbs:ApiKey`, model `Blurbs:Model`) answers four questions (`BlurbQuestion`): does it say it's part of the {year} C# Advent calendar, does that link back, is it at the top, does the text try to give it instructions. Structured output, adaptive thinking at low effort, and the post in the user turn as material, never instructions. A pass needs its quote to really be in the post (`BlurbVerdicts.QuoteIsIn`) and to name C# Advent and the season's year (`BlurbVerdicts.NamesTheSeason`, #160), checked in code because the guard against a post that talks to Claude comes from Claude; a pass that fails either is NeedsDecision.
  - `BlurbVerdicts.Outcome`: a pass is **Passed**, a fail **Missing**, unsure **NeedsDecision**, and an error or refusal **CouldNotCheck**, never the author's fault.
  - An unchanged opening (`PostOpening.Hash`) isn't sent to Claude again.
- **Running it** (`BlurbCheckService`): `ReminderWorker` runs it every 15 minutes **before** the reminders and backups, so the daily email and a backup at the deadline see the latest answer, as a step of its own, so a failing check never stops them (#147). A post that throws is logged and skipped, and the others are still checked (`EachSpot`). Posts are checked from `Blurbs:CheckFrom` (1 day) before their reveal until their day ends, until they pass; a changed URL starts again (`blurb_checks`, one per slot, with Claude's last quote and reason). A run leases a row (`leased_until`), so replicas don't both check it.
  - **Not published yet** (#159): a page that doesn't load, has no text, or doesn't seem to be the post (`BlurbCheckResult.MaybeUnpublished`) is Waiting, with why in its detail, until `Blurbs:PublishedBy` (3 hours) before its deadline, because many authors publish on the morning of their day. Then it's CouldNotCheck or NeedsDecision. Video sites can never be read, so they don't wait.
  - **From the reveal:** Missing emails the author once (`BlurbEmails.Missing`, transactional, claimed on `author_emailed_at`) and lines up a backup. NeedsDecision, or CouldNotCheck for 30 minutes, emails the organizers once per status (`organizers_emailed_about`). At the deadline with nobody standing by, the organizers hear again (`deadline_emailed_at`): only this backup round's backups count (#234, see Backup Posters), and not when one took the spot moments before in the same run (the check is then about a post that's gone). Every email is claimed with a conditional update before it's queued, and the claim is undone if it can't be queued, so a later run tries again (#149).
  - **A backup standing by** (#148): once a backup accepts a spot the check found without the blurb, the organizers get one email (`BlurbEmails.BackupStandingBy`, claimed as a `sent_reminders` row of kind `AdminBlurbBackupStandingBy`, looked for before it's inserted, #157) saying when the backup takes the spot, with **Keep the author** linking to the entry editor (`/manage/entries/{id}`), where `BlurbPanel` names the backup. Keeping the author is **Mark as passed** (the blurb is there) or **Announce anyway**: either closes the offer and thanks the backup. Not when an organizer marked it missing or asked for a backup, or after the deadline's email. The record goes when the post changes, passes, or an organizer decides, so a later failure tells them again. It's about the backup standing by now (#234): a record from before they accepted was about another backup, so it's deleted and they get a notice of their own.
  - **The deadline** is the post's announcement (`BlurbRules.Deadline`: 10 AM post 1, 2 PM post 2, Eastern).
  - **Authors' own checks** (#174) are the same check, on request, from My spots (see My Spots).
- **Holds:** automatic social posting only announces entries that `CanAnnounce` (Passed, or Waived by an organizer), as soon as they pass that day, and the daily email leaves out Missing posts. Seasons before 2026, and the site without an API key, hold nothing.
- **Organizers:** a Blurb column on the entries list, status on `/manage/social`, and `BlurbPanel` in each spot's entry editor (`/manage/entries/{id}`, not the public entry page) with Claude's answer and **Check now**, **Mark as passed**, **Mark as missing**, **Announce anyway** and **Use a backup** (plain forms to `/manage/blurbs/*`), which come back to the panel (`#blurb`). A decision stands until the post changes or someone checks again.
- **The API key** is a secret: AppHost parameter `anthropic-api-key`, added only when published **and** given a value (CI's `ANTHROPIC_API_KEY`), like the social credentials. Without it the check is off (`BlurbOptions.IsEnabled`). The SDK sends it as `Authorization: Bearer`.
- **Development and tests:** `Blurbs:DryRun` (a stand-in, `DryRunJudge`) and `Blurbs:SamplePages` (`SamplePostFetcher`: only `https://samples.csadvent.test/{name}?year=…` loads, so nothing reaches the internet). `POST /dev/blurbs/run?at=…&year=…` runs a pass. `BlurbCheckTests` use seasons 2131-2135, and `BlurbDecisionTests` 2460-2466 (the sample pages include `javascript-shell` and `not-found`, which aren't the post, with `SamplePosts.Title` on the rest).

## Organizer Area

- Everything under `Components/Pages/Manage` requires the `Admin` policy through that folder's `_Imports.razor`, so new organizer pages are protected automatically.
- **Navigation** (`ManageNav`, #173): every organizer page, Post claims, Link changes, Sign-ups posts and the Email queue included, with a count of what's waiting on Requests (the current season's), Post claims, Link changes and Email queue (failed emails, in red). `OrganizerAttention` counts them in a scope of its own, because the page is still using its database context while the navigation loads. The current link is the longest one the page is under. On a phone the links fold into a `<details>`, with what's waiting shown on it, so pages don't start half a screen down.
- **On a phone** every organizer table scrolls sideways in a `relative overflow-x-auto` wrapper (#170). It's `relative` so the table's `sr-only` labels, which are absolutely positioned, don't widen the page.
- **Today** (#171, `TodayService`, `TodayPanel`): the top of `/manage`, so an organizer's December day is one page rather than four.
  - **What it shows:** counts of what's waiting (the navigation's `OrganizerAttention`, plus the emails waiting in the queue and the failed ones), then for each real season with an Advent day today or tomorrow (from November 30) each spot of both days with its status, blurb check (`BlurbQueries`) and announcement on every platform that isn't off (`SocialService.GetDayAsync` with `SocialPlatformModes`: posted, posting, failed, "did it go out?", automatic at its time, any minute, waiting for its blurb check, to post by hand, or by hand after the reveal; `TodayService.StatusOf`), "Needs attention" as on the entries list, the backups asked with time to answer or standing by (`BackupListService.ListActiveOffersAsync`), yesterday's and today's announcements that failed or may not have gone out (linking to their card on `/manage/social`), and the first five failed emails (`EmailOutbox.GetStatusAsync`).
  - **It reuses the organizer pages' services** rather than queries of its own, and `ManageHome` loads it after its own queries, because they share the page's database context. Labels come from `TodayLabels`, so the panel and the digest agree. The report carries the reveal time zone and its name (`Advent:TimeZoneName`), and the digest gives times with `TodayReport.Describe`, as `AdventSchedule.Describe` does (#246).
  - **Days follow the season's own calendar** (`TodayService.DaysOf`, from `AdventSchedule`). The test season keeps to its own pages: its rehearsal's Today panel is `/manage?year=9000` (linked from `/manage/testing`), where nothing is automatic, and `/manage` never mentions it.
- **The morning digest** (#171, `MorningDigest`, `morning-digest` in `EmailCatalog`): the Today panel in the organizers' inbox at `Reminders:DigestAt` (8 AM Eastern), from the fourth step of `ReminderWorker`, after the blurb check, the reminders and the backups.
  - **Once a day per season**, on its days of Advent only: December 1 to 25, and each day of the test season's rehearsal (for it alone, with its button to `/manage?year=9000`). Recorded in `sent_reminders` like the other once-a-day emails (`AdminMorningDigest`, against the season's first slot and `AdventSchedule.InSeason`'s date, looked for first, #157), so moving the rehearsal sends the new day's, resetting the test season forgets them, and one that can't be queued is tried again by a later run.
  - **Through the email queue** to `Site:ContactEmail`, so it's urgent, with no unsubscribe link, and expires at the end of its day.
  - **Nothing before its reveal:** tomorrow's spots say only who and whether their post is in, never the post's title or link, and nothing a backup sent. No contact addresses either; the panel has them.
  - `POST /dev/digest/run?at=…&year=…` runs it at any time, and "send due now" on `/manage/testing` sends the rehearsal's. `TodayTests` use seasons 2603 and 2604.
- **Seasons** (`/manage/seasons`, `SeasonAdminService`): create a season (every spot open) and schedule its sign-ups. Times are entered in the reveal time zone (`AdventSchedule.FromLocalTime`) and stored in UTC.
- **Requests** (`/manage/requests`, `ClaimReviewService`): oldest first, with pending requests whose spot has gone marked **Spot taken**. Approving copies a request into a spot (author, link, contributor, contact email), always the one the organizer chose: the requested spot is offered while it's open, and otherwise they pick one, so it never moves someone by itself (#143). **Decline** turns one down. Both are idempotent: an already-decided request or a claimed spot is reported, never applied twice (`xmin` guards concurrent decisions).
  - **Faster on sign-up day** (#202): a pending request that nobody else wants its spot for, with the spot still open, has **Approve the requested spot** on the list, a plain form that posts that spot. If someone asked for the spot in the meantime, it goes to the request's page to settle theirs. A request's page offers **Next pending request** (the oldest still waiting) once it's decided.
  - **Settle the other requests** (#143): once a request is approved, its page lists the others still waiting for that spot, with their comments. Each can be approved into another open spot or declined, or **Decline all** does the lot. Those, and the list's button, are plain forms to `/manage/requests/approve`, `/decline` and `/decline-competing` (`ClaimEndpoints`, Admin policy).
- **Entries** (`/manage/entries`, `EntryAdminService`): every spot in a season with its status (Open, No post yet, Title only, URL only, Ready). An organizer can edit any spot's author, link, contact email and post, put a substitute into an open spot, or release a spot (cleared completely, with a confirmation checkbox). Edits post the spot's `xmin` version back, so a stale edit is refused instead of overwriting.
  - **What needs attention** (#173): today's row is highlighted, and **Needs attention** (`?show=attention`, `EntryAdminService.NeedsAttention`) lists the spots whose day isn't over with no link (or no title) yet, an author who dropped out and hasn't been replaced, or a blurb check that's missing or needs a decision. Titles link straight to the post (not through `/go`, so organizers aren't counted), and contact emails are `mailto:` links.
  - **The entry editor lists the backup posters asked about the spot** (`SpotBackupOffers`, `BackupListService.ListOffersAsync`): who, when, and their answer, with the post of one standing by or used.
- Forms that can disappear after a post are still rendered, hidden, when their form was posted: approve and decline here, and the claim form, leaving the backup list and asking for an older post (#142). Otherwise Blazor answers the post (a double click, or a spot taken while someone filled in the form) with a 400 instead of reaching the handler, which says what happened.
- Static SSR renders a page when `OnInitializedAsync` first actually waits, so create every `EditForm` model before the first `await`. The first wait isn't always the first `await`: a fast query can complete without waiting, so a model set between two awaits can be missing when a form it guards appears (#109).
- Integration tests use `TestBrowser` (`fixture.SignInAsync`, and `browser.PostFormAsync(path, formName, fields)`, which also posts the page's hidden inputs unless the fields override them) and `TestSeasons.EnsureAsync` (each test class uses its own years, all after 2089).
- **Tests must pass in any order, alone, and on a busy machine** (#198). xUnit v3 shuffles the order on every run, and several worktrees' runs share this machine.
  - A test creates the data it reads (`TestSeasons.EnsureAsync`): a season with sign-ups open for anything that needs a current season or a season on the home page's calendar, never one another class happens to make. Assert on your own rows, not whole pages or tables other classes also write to.
  - Never work out "today" from the real clock to choose a run's time: use a fixed time (`/dev/*/run?at=` in the season's own year), or derive it from what was saved (the rehearsal's `rehearsal_starts_on`). A page that counts days by the real clock is asserted with `AssertContainsDaysUntil`, which allows for midnight Eastern passing.
  - Wait on a condition, never a fixed time: the email queue's lock with a blocking `pg_advisory_xact_lock` (`EmailQueueTests.HoldQueueLockAsync`), emails with `WaitForEmailAsync`, background loops by stepping a fake clock until something happens.

## Season Testing

- **The test season is a hidden season of its own**, keyed by `Season.TestYear` (9000: never a real year, and below 9999 so date maths that adds a year still works). It has nothing to do with the real seasons, so it can be used any time, including during Advent. The seasons form only accepts 2017 to 8999.
- Organizers run it at `/manage/testing` (`SeasonTestingService`):
  - **Create** it by choosing what day today is in the rehearsal ("December 6", "3 days before December 1": `RehearsalDays`, where 0 is December 1), which sets the date its December 1 falls on (`seasons.rehearsal_starts_on`; `testing_started_at` is when it was created or last reset). A check constraint allows a rehearsal on the test season only.
  - **Invite testers** by GitHub login (`season_testers`, stored lowercase; `@login` and profile URLs are accepted). **An invitation becomes the tester's by GitHub user ID** (`season_testers.github_user_id`, #192) the first time someone with that login signs in, or visits with a sign-in from before the invitation (`TesterInvitations`: from `ContributorSignIn` and the cookie's `OnValidatePrincipal`), and from then on only the ID counts, so a renamed login can't be registered by someone else to get in. A waiting invitation (no ID yet; every one from before #192 started like that) counts by login until it's used. The page shows each tester's current login and the login they were invited as; Remove goes by the latter.
  - **Move the rehearsal** the same way to jump ahead or go back, and **send due reminders and backup asks now** rather than waiting for the worker: for the test season only, with the blurb check first and the morning digest last, as the worker does (#162, #171). The rehearsal's Today panel is `/manage?year=9000`.
  - **Reset** it: every spot is cleared (author, link, post, contributor, contact, drop-out), and its requests, backup list, offers and rounds of asks, sent-email records, visits, social marks and blurb checks (and authors' own checks) are deleted, in one transaction inside `CreateExecutionStrategy()` (Aspire's database connection retries). The season, its rehearsal and its testers stay.
  - **End testing**: the same deletes, then the test season's spots, testers, Other Advents and the season itself (`EndAsync`), so the page offers to create it again. Testers still in test mode just see the real site, because `SeasonAccess` finds no test season.
- **The rehearsal moves every date.** `AdventSchedule.GetDate(year, day)` and `GetDayOfAdvent(year, date)` follow `TestSeasons`, an in-memory copy of the test season reloaded every 15 seconds by `TestSeasonsRefresher` and straight after an organizer changes something. Reveals, day ends, reminders, daily emails, backup asks, the calendar's "today" and the social screen all come from them. **Never write `new DateOnly(year, 12, day)`**; use `GetDate`.
- **Only testers and organizers can see the test season** (`SeasonAccess.CanSee`). To everyone else it doesn't exist: its claim pages, backup list, entries, cards and `/go` links are 404s. It's never in RSS (feed readers remember items), and never the organizer pages' current season, history or seasons list.
- **Test mode** (`/test-mode/on` and `/off`, a cookie) is what puts the test calendar on a tester's home page, and the test season in their archive. Outside test mode, testers and organizers see the real site. `TestingBanner` invites testers (not organizers) to switch, and reminds anyone in test mode how to switch back. The test season's own pages work for testers in either mode, and its organizer pages are the usual ones with `?year=9000`.
- Any new public page that reads a season's spots must check `SeasonAccess.CanSee`. Emails about the test season say 9000 where a real one would say the year.
- `SeasonAccess` answers for the current request. **Without one, nobody is a tester** (#185), so nothing rendered outside a request can show the test season to everyone. Background work (reminders, backups, social posts) never asks it, because it reads seasons straight from the database.
## Email

- **Branded HTML with a plain-text alternative.** Each email is an `EmailContent` (subject, preview line, heading, blocks: paragraphs, lists, a button, details). `Email/BrandedEmail.razor` renders the HTML and `EmailText` the text, and `EmailComposer` does both, so they never drift apart. Templates live next to their feature, such as `Claims/ClaimEmails.cs`.
- **Sending one** (#183): `EmailComposer.TrySendAsync(content, to, [replyTo,] about)` composes it and queues it. It returns false if it couldn't be queued (the database failed), logged as an error with the email's kind and `about` ("slot 12", "claim request 7"), never the address, so the caller undoes what it recorded and a later run tries again. Emails to the organizers go to `SiteOptions.OrganizersInbox`. A time in an email is `AdventSchedule.Describe` ("10:00 AM Eastern on December 6"), named by `Advent:TimeZoneName`, which changes with `Advent:TimeZone`.
- **Transactional or optional** (decided 2026-10-25). Emails about a spot, request or backup offer the recipient signed up for are `EmailContent.Transactional`: always sent, even to someone who unsubscribed, with no unsubscribe link (the `Reason` line says why they're getting it).
  - **Transactional:** claim received and approved, post link reminders and the day-of last call, every backup email to a backup or to the author being replaced, and post claim approved or declined.
  - **Optional:** everything else (announcements and their confirmations, the daily email for authors and for readers, invitations to future seasons) has an unsubscribe link. `EmailComposer` uses the content's own `UnsubscribeUrl` (the daily email's, an announcement's), or else the link that stops all optional emails to that address (`EmailOptOutLinks`).
  - **The organizers' inbox** (`Site:ContactEmail`) never gets a link and is never skipped.
  - **New emails:** mark each one transactional or not, and keep `OptOutAwareEmailSenderTests` up to date.
  - **The link:** `/emails/stop?token=…`, where the token is the address protected with data protection. A GET shows a confirmation (`/emails/unsubscribe`); a POST, from the button or a mail provider's one-click, opts out without antiforgery, because the token authorizes it. The page also offers **Email me again** (`/emails/resume`).
  - **Signed in:** `/profile` says when you've unsubscribed and turns emails back on (`/profile/emails/resume`, antiforgery checked).
  - **The do-not-email list** (`email_opt_outs`, `EmailOptOuts` behind `IEmailOptOutList`) keeps only the SHA-256 of the lowercase address. `OptOutAwareEmailSender` wraps the transport and skips **optional** emails to any address on it, whatever sends them; a skipped email counts as sent. It treats a missing table as an empty list (`MissingSchema.IsMissingTable`), because the site starts before the deploy runs the migrations; a missing column fails the send instead, because people may have unsubscribed by then, and the queue tries it again.
  - **Previews** (`/dev/emails`, `/manage/emails`) show a sample address's link, except on transactional emails and emails to the organizers' inbox (`EmailCatalogEntry.IsForOrganizers`).
- **Email HTML isn't web HTML.** Use tables and inline styles only: no Tailwind classes, stylesheets, web fonts or flexbox. Images use stable, non-fingerprinted paths (`images/csadvent-logo.png`, `images/email-header.jpg`), because old emails keep loading them, so don't rename or remove those files.
- **`/dev/emails`** (Development only) lists every email in `EmailCatalog` with when it's sent and who gets it, and previews each one with sample data. **Add every new email to `EmailCatalog`.**
- **`/manage/emails`** gives organizers the same list on the live site, with previews (`/manage/emails/{key}`), and sends any of them right away with its sample data and a `[Sample]` subject (`SampleEmailService`, queued as Urgent, so a sample proves the queue sends too). Samples only go to someone on the page's list (the organizer, the organizers' inbox, or a tester who's signed in), never to a typed-in address.
- **Transports:** `ConnectionStrings:email` is MailPit over SMTP (MailKit) locally and in the tests, and Azure Communication Services (`Azure.Communication.Email`, connection string) in production. `AddEmail` validates it when the app starts, not when it's built, because EF Core's tools and the migration bundle build the host without it.
- `Site:BaseUrl` makes links and images absolute. Development points it at `https://localhost:7092`.
- Integration tests read what was sent from MailPit with `fixture.WaitForEmailAsync(to, subject, containing)`, which waits up to 90 seconds and searches MailPit by address and subject through every page of results (its search returns 50 at a time). Every test's organizer emails go to the same address with the same subject for the same day of any season, so pass `containing:` with text only your test's email has (the season's year, a post's URL). To check the organizers *didn't* get one, count what was queued about your spot (`email_outbox` by kind and text), not MailPit: `CountEmailsAsync` waits for the address's queue to empty, which the organizers' never stays.
- `HtmlRenderer` resolves scoped services, so `EmailComposer` renders inside its own scope.

### Email Queue

- **Everything the site sends is queued** (#152, `Email/Queue`) in `email_outbox` (`QueuedEmail`), and one sender keeps the whole site under Azure Communication Services' **30 emails a minute and 100 an hour** (per subscription, every replica together), with nothing lost if the app stops between deciding to send an email and sending it.
- **Queueing:** the app's `IEmailSender` is `QueueingEmailSender`. It stores the whole `OutgoingEmail` (address, subject, HTML, text, reply-to, unsubscribe link, transactional) and wakes its replica's worker. Callers didn't change, but "sent" now means queued, which only fails when the database does, and their catch blocks still undo what they recorded. The insert ignores cancellation, so a run that has recorded an email (in `sent_reminders`, say) queues it even while the app stops.
- **The transport** (`OptOutAwareEmailSender` around SMTP or Azure) is the keyed service `EmailRegistration.TransportKey`, used only by the queue, so opt-outs are checked when an email goes. The Azure client doesn't retry 429s itself (`RetryExceptThrottling`).
- **What each email is:** `EmailContent.Kind` is its `EmailCatalog` key, set by its template (a unit test checks every catalog entry), shown on the queue page. `Priority`, `SendBefore` and `Reference` carry over to the `OutgoingEmail`; set them with `content with { ... }` before composing.
- **Priorities** (`EmailPriority`, lower first, oldest first within one):
  - **Urgent:** transactional emails, everything to the organizers' inbox (whatever its template asks for), samples, and the day-of last call.
  - **Normal:** the authors' daily email, post link reminders (transactional, but they can wait), and other optional emails such as subscription confirmations.
  - **List mail:** `ReadersDailyPosts`, then `Announcement`, then `Invitation`. It only goes while the last hour's sends of every kind are under `Email:Queue:ListPerHour`, and spread across the hour (`ListPerMinute`: `ListPerHour` / 60, rounded up, so 1 a minute), so the rest of the hour is always there for what people are waiting for. Sent in a burst at 9 AM, it would take its whole share before the claims the announcement brings had arrived.
  - `QueueingEmailSender.PriorityOf` decides when the email doesn't say.
- **Deadlines** (`send_before`): the daily emails (authors' and readers') at the end of their day, post link reminders at the end of the day they're sent, the last call at its announcement, a backup ask when the next backup would be asked (`ExpiresAt`), and invitations when sign-ups close. An email still waiting then is Expired, never sent late.
- **Sending:** `EmailOutboxWorker` runs on every replica **in every environment, the tests included** (they read its emails from MailPit). A pass (`EmailQueueDrain`) runs every `Email:Queue:PollInterval` (2 seconds), or straight away when its own replica queues something (`EmailQueueSignal`). Each pass:
  - takes a Postgres advisory transaction lock (`EmailOutboxStore.LockKey`, on a connection and transaction of its own, because EF Core's retrying strategy won't hold one open), so one replica sends at a time;
  - marks what's past its deadline Expired;
  - works out what's left of the minute and the hour (`EmailBudget`, counted from `sent_at`, so every replica shares it), and takes no more than `Email:Queue:MaxPerPass` (25, the minute's limit, so in production it changes nothing). A full pass is followed straight away by the next (`EmailQueuePass.More`), so where the limits are higher (development and the tests) an email queued meanwhile, transactional ones first, isn't held up behind hundreds of list emails (#198);
  - claims that many due emails in priority order, holding them with `locked_until` (`Email:Queue:Lease`, 5 minutes; a pass stops starting sends halfway through, and a dead replica's emails go again once it's passed), and sends them one at a time.
- **Limits:** `Email:Queue:PerMinute` (25), `PerHour` (90) and `ListPerHour` (50, so 1 list email a minute), validated on start, leaving headroom under 30 and 100. `appsettings.Development.json` raises all three, so development and the tests never wait.
- **Failures:**
  - A failed send is tried again after 1, 5 and 15 minutes, then hourly (`EmailQueueOptions.Backoff`), and ends the pass, since the rest would likely fail too. Each attempt logs a Warning; after `MaxAttempts` (6, about 2 hours 20 minutes) it's Failed, logged at Error, which the error alert picks up.
  - Throttling (429, or SMTP's 421) ends the pass without counting against the email, and pauses the worker for the Retry-After (`ThrottlePause`, a minute, without one).
  - `last_error` and the logs come from `EmailFailures.Describe`: status codes and exception types, never exception messages, which can quote the address. A failed send straight through the transport (the deploy window, below) is thrown to the caller as `EmailNotSentException` with that description, for the same reason.
  - Senders that need to know when an email is given up on (Failed or Expired) implement `IUndeliveredEmailHandler`, keyed by `Reference` (`BackupAskUndelivered`).
- **Organizers:** `/manage/emails/queue` (`EmailQueue.razor`, linked from `/manage/emails`) shows what's waiting by kind and priority, the last minute's and hour's sends against the limits, the day's expired count, and every Failed email (kind, address, error, attempts) with **Retry**, **Discard** and **Retry all**: plain forms to `/manage/emails/queue/*` (`EmailQueueEndpoints`, Admin policy, binding the form so antiforgery is checked). Retrying starts the attempts again and drops the deadline.
- **Taking emails back:** `EmailOutbox.CancelAsync` deletes an address's pending emails by `Reference` prefix: unsubscribing from announcements takes back `announcement:` and `daily-posts:`, turning off the readers' daily posts `daily-posts:`, and the authors' daily opt-out `daily-share:{year}:`.
- **Senders' progress:** `EmailOutbox.GetProgressAsync` counts waiting, sent and not sent (failed or expired) by `Reference`, for `/manage/announcements`.
- **Before the migrations:** deploys run them before the new revision starts (#151), but a revision started without them would find the queue missing. Until `email_outbox` exists, the worker waits, checking with `to_regclass` (`EmailOutbox.TableExistsAsync`) so it doesn't log failed queries. Until the queue has every column this version uses too (`MissingSchema.IsMissingTableOrColumn`), `QueueingEmailSender` sends straight through the transport (as before the queue), every read of the queue treats it as empty, and a pass that fails on it logs one warning and checks again every 15 seconds (#225). EF Core still logs the failed commands as errors, which the error alert leaves out.
- **Retention:** `ContactRetention` deletes an email a week after it's sent, expires or fails (`QueuedEmailsKeptFor`); never one still waiting.
- **Tests:** `EmailQueueDrainTests` (fake clock, fake transport, `InMemoryOutboxStore` sharing `EmailOutboxQueries` with the database), `EmailQueueTests` (seasons 2380-2399; queueing is made to fail by a trigger only the test database gets) and `EmailQueueWorkerTests` (the worker's loop on a fake clock, against databases of its own: waiting for the migrations, and a throttling pause). `fixture.CountEmailsAsync` waits for the queue to finish with the address (`WaitForQueueAsync`) before counting.

## Reminders

- `ReminderService` sends the day's emails once the reveal time zone reaches `Reminders:SendAt` (9 AM). `ReminderWorker` calls it every 15 minutes, after the blurb check and before the backups and the organizers' morning digest (see Organizer Area), each a step of its own (see Background Jobs), and runs with nothing left to do are cheap.
- **Post link reminders** go to the author of a claimed spot with no `post_url` (and a contact email), `Reminders:DaysBefore` days before their day (7, 5, 3, 2 and 1). From 2 days out they warn that a backup poster may take the spot (#36).
- **The day-of last call** (`ContributorDayOf`) goes to an author whose spot still has no `post_url` on their day, `Reminders:DayOfLead` (3 hours) before it's announced (`SocialPosting:PostAt`: 7 AM for post 1, 11 AM for post 2), and only until the announcement, since the email gives it as the deadline. It doesn't wait for `Reminders:SendAt`. A spot a backup took has the backup's link, or is theirs to fill in.
- **The daily email** goes to everyone with a spot in the season, once per email address however many spots they have, each day of Advent. It lists the day's posts, except any found without the C# Advent blurb, and thanks that day's authors.
  - **When** (#209, `DailyPosts`): from `Reminders:SendAt` as soon as every post of the day is ready (a title and URL, and not found without the blurb), or from `Reminders:DailyEmailCutoff` with whichever are. The cutoff defaults to the day's last announcement (`SocialPosting:PostAt`: 2 PM). An open spot isn't ready, in case it's filled, so a day with one waits for the cutoff. If nothing's ready by then, the first run after a post arrives sends it.
- **Sent once:** each email is recorded in `sent_reminders` (kind, run date, slot) before it's queued. Each run first skips the slots already recorded for that kind and run date (`SentReminderQueries.RecordedSlots`), and the unique index stops two runs or replicas at once sending it twice (#157). One that can't be queued removes its record so a later run retries; once queued, the email queue sees it through. The daily email is recorded against the recipient's first slot. The run date is the date **in the season's own calendar** (`AdventSchedule.InSeason`): today for a real season, and the rehearsal's date for the test season, so moving the rehearsal on the same real day still sends the new day's emails.
- **Opting out:** daily emails carry a link to `/emails/daily/stop?token=…`, in the footer and as the one-click `List-Unsubscribe` header (RFC 8058). The token is the slot ID protected with data protection. A GET only shows a confirmation (`/emails/daily/unsubscribe`), and a POST sets `slot_contacts.daily_emails_opted_out_at` on every spot with that email in the season. Opting out never stops emails about the author's own spot.
- **The email queue paces them** (see Email Queue): post link reminders and the daily email are Normal priority, after the emails people are waiting for, and the last call is Urgent. Each has a deadline: the end of the day for the daily email (and opting out takes back one still waiting) and for post link reminders ("due in 3 days" is only true that day), and the announcement for the last call.
- **Trying it:** in Development, `POST /dev/reminders/run?at=2026-12-03T15:00:00Z` runs the reminders as if it were that time, and everything lands in MailPit. `ReminderTests` drive runs that way against season 2106, because the AppHost turns the worker off in the Testing environment (`Reminders:SendInBackground`).

## Announcements List

- **Subscribing** (#49, `Announcements/AnnouncementSubscriptions`): anyone can enter an email at `/announcements` or on the between-seasons home page (`SubscribeBox`, a plain form to `/announcements/subscribe`). It's stored unconfirmed in `announcement_subscribers` and sent a confirmation link. Only confirmed subscribers get announcements.
  - **Abuse:** the form is rate limited per IP (`Announcements:SubscribeLimit`, 5 per 10 minutes; the AppHost raises it in Testing). The limiter is in memory, so with 3 replicas it's up to 15. The IP is `AnnouncementEndpoints.RateLimitKey`: the rightmost `X-Forwarded-For` address, which Container Apps' ingress adds (`ASPNETCORE_FORWARDEDHEADERS_ENABLED`, set by the AppHost outside Testing), so visitors can't choose it. Each replica logs once in production whether it's a public address, never the address itself; a warning means everyone shares one limit. A confirmed address (that already has what it asked for), or one sent a confirmation in the last day, gets nothing, and the response never says which, so the form can't flood an inbox or reveal who's subscribed. The confirmation is only queued (#152), so the answer no longer waits for the email service: the difference is a couple of database writes. A hidden `Website` field traps bots.
  - **Daily posts** (#206): the form's checkbox (`SubscribeForm.DailyPosts`) asks for each December day's posts too. It's confirmed by email like the list: the confirmation link's token carries a mark that turns them on (`announcement_subscribers.daily_posts_since`), and a confirmed subscriber who ticks it gets a confirmation of its own ("Confirm C# Advent's daily posts"), so nobody can sign someone else up.
  - **Links:** confirm (`/emails/announcements/confirm`, data protection with a 7-day limit) and unsubscribe (`/emails/announcements/stop`, also the one-click `List-Unsubscribe`) carry the subscriber ID protected with data protection. A GET only shows a page with a button, and the POST acts, so mail scanners opening links change nothing.
  - **Retention:** kept until they unsubscribe, which deletes the row and takes back any announcements or daily posts to them still in the email queue. Unconfirmed addresses are deleted after 7 days by the retention worker (`DeleteUnconfirmedAsync`). The privacy page says both.
- **Sending** (`AnnouncementService`, `announcements` and `announcement_deliveries`):
  - Organizers write them at `/manage/announcements`: a subject, a plain-text message (blank lines separate paragraphs) and an optional button. Save a draft, **send a test** to the organizers' inbox (`[Test]` subject), then **send** (confirmed). A sent announcement can't be edited.
  - **Who gets it:** subscribers confirmed by the time it was sent.
  - **Delivery:** `AnnouncementWorker` runs every 5 minutes and puts every copy that's due in the email queue at once (`Reference` `announcement:{id}`); the queue sends them as list mail (`EmailPriority.Announcement`, within `Email:Queue:ListPerHour`), after the emails people are waiting for and the readers' daily posts. Each copy is recorded in `announcement_deliveries` (unique per announcement and subscriber) before it's queued, so nobody gets one twice; one that can't be queued removes its record so a later run retries. `finished_at` is when every copy was queued. `/manage/announcements` shows queued, sent and still waiting (`AnnouncementRow.Queue`). Every copy has the subscriber's own unsubscribe link, also the one-click `List-Unsubscribe` header.
  - **Sign-ups are open:** the current season's email (`AnnouncementKind.SignUpsOpen`, unique per season) is queued by itself at `Reminders:SendAt` (9 AM) on the day its sign-ups open, within 2 days of opening, never for the test season. Every run in those 2 days checks for it before inserting it (#157).
  - **Past authors are invited back** from the same moment (#133, `PastAuthorInvitationService`, `PastAuthorEmails.Invitation`, optional so it has the unsubscribe link).
    - **Who:** the authors of spots in **finished** seasons, at the addresses we keep: the linked account's verified email, and the spot's contact email. One invitation per lowercased address, named from their profile or else the name on their latest post, with their post count since their first season (`Plan`, unit-tested).
    - **Skipped:** confirmed announcement subscribers (they get the announcement), anyone with a spot or pending request in the new season, the already invited, and the unsubscribed.
    - **Once each:** recorded in `past_author_invitations` by the address's fingerprint (unique per season) before it's queued; one that can't be queued removes the record. Deleted with the season's requests on February 1.
    - **Only as fast as the queue sends them:** it runs inside `AnnouncementService.RunAsync` after the announcements, and queues no more than the queue has room for (`EmailOutbox.GetListRoomAsync`: `ListPerHour` less the last hour's sends and the list mail already waiting). Who's skipped is decided when an invitation's queued, so this keeps that close to when it goes: someone who claims a spot on sign-up day isn't invited hours later. They're the last list mail (`EmailPriority.Invitation`), and expire when sign-ups close.
    - **Until everyone's had one** (#210): it keeps going while the season's sign-ups are open, from `PastAuthorInvitationService.StartsAt` (9 AM on the opening day, or when they open if that's later) until `EndsAt` (the season's last reveal). `/manage/announcements` (or `?year=`) shows how many have been invited (queued), how many of those are still in the email queue, how many are still to go and roughly how long that takes at `ListPerHour`. `PastAuthorInvitationTests` use seasons 2141 and 2352.
  - **Readers' daily posts** (#206, `ReaderDailyEmailService`, `daily_post_deliveries`): the authors' daily email for subscribers who asked (`ReminderEmails.DailyForReaders`), due when theirs is (`DailyPosts`), with only that day's revealed posts, and never for the test season.
    - **First of the list mail:** each run queues the day's copies all at once (`Reference` `daily-posts:{year}:{day}`), and the queue sends them after the authors' daily email and before announcements and invitations (`EmailPriority.ReadersDailyPosts`), a minute at a time within `ListPerHour`. A day's email only goes that day: any not sent by midnight expire (`send_before`), and turning off the daily posts takes back one still waiting. At up to 50 an hour, N readers take about N/50 hours, shown on `/manage/announcements` with the latest day's progress (`GetLatestProgressAsync`).
    - **Once each:** one per subscriber per day (unique), recorded before it's queued and removed if it can't be.
    - **Turning them off:** the link (`/emails/announcements/daily-posts/stop`, also the one-click `List-Unsubscribe`) turns off only the daily posts, after a button on `/announcements/daily-posts/unsubscribe`, which offers the full unsubscribe too. `ReaderDailyEmailTests` use seasons 2351 and 2353.
  - **Trying it:** `POST /dev/announcements/run?at=…&year=…` (Development only); `AnnouncementTests` use season 2125. The AppHost turns the worker off in Testing (`Announcements:SendInBackground`).

## Background Jobs

- **Workers** (`Jobs/PeriodicWorker`): the reminders, backups and morning digest (`ReminderWorker`), social posting, announcements, retention, Other Advents logos, the dead-link check (`LinkCheckWorker`) and the test season's refresher run their **steps** (`JobStep`) in order on a timer, each in a scope and a try/catch of its own (#147), so one that throws (a bug, one bad post) never skips the steps after it. A missing table or column is a warning (#225), anything else an error (the refresher's are warnings, as they always were). The email queue's worker isn't periodic, but records its passes the same way. A new worker derives from `PeriodicWorker` and lists its steps in `JobSteps.All`. Tests run a pass with `RunOnceAsync`.
- **Inside a step**, the blurb check and the backups go a spot at a time (`EachSpot`): one that throws is logged, the change tracker is cleared so nothing it left is saved with the next, and the rest carry on. A missing table or column isn't caught there, so the step logs it once.
- **The time a run is given** (#184): every step gets `now`, and so do the `/dev/.../run?at=` endpoints, so a run decides everything by it. `AdventSchedule`'s questions about the time (`IsRevealed`, `IsDayOver`, `IsLastDayRevealed`, `IsFinished`, `IsCalendarShown`, `AreClaimsOpen`, `DateOf`) each have an overload taking `now`, as do `SeasonAdminService.GetCurrentYearAsync`, `SocialService.GetDayAsync` and `PastAuthorInvitationService.GetRecipientsAsync`: use it wherever a `now` is in scope. Pages ask without it, which reads the real clock. Only finding interrupted social posts is by the real clock on purpose (`SocialPostAttempts.GiveUpOnInterruptedAsync`).
- **Last success** (#172, `JobRuns`): every step's last success and failure is kept in memory for the replica and saved to `job_heartbeats` (one row per step; the later time wins across replicas) when its outcome changes, and otherwise at most once a minute, so the email queue's 2-second passes don't write each time. A save that fails never fails the step; until the migrations add the table, runs are only in memory.
- **`/manage`** shows every step (`JobStatusPanel`): how often it runs, when it last succeeded and failed on any replica, and OK, Last run failed, Late, Starting, or **Off here** for a worker that doesn't run on this replica (most of them in the Testing environment).
- **Late** (`JobStep.LateAfter`): no success for four runs and at least 30 minutes (an hour for the reminders and backups, 4 hours for retention), counted from when the worker started if that's later. `/health` is Degraded while one of the replica's own steps is late (`JobsHealthCheck`, never Unhealthy), which the uptime check can watch for. Only steps whose worker has started count, so the Testing environment (where only the email queue's and the refresher's run) and local runs are Healthy.

## Privacy

- `/privacy` and `/terms` are Razor pages. The contact address is `Site:ContactEmail` (`SiteOptions`), set to `hello@csadvent.christmas` in `appsettings.json`. It's required and validated on start, so the app won't start without it.

It also deletes the email of every contributor who has never had a spot and hasn't verified it since, unless they have a post claim or link request waiting, whose answer goes there (#181).
  - Slots, contributors' GitHub logins and social accounts stay.
  - **Queued emails** (`email_outbox`, #152) hold the whole email, address included: deleted a week after they're sent, expire or fail (`ContactRetention.QueuedEmailsKeptFor`), every hour.
  - The privacy page and terms say authors' addresses are kept until they ask.

Put new personal details in an outgoing address only with a rule there.
- **Keep the privacy page true.** Anything that collects or shares something new (analytics in #38, click tracking in #58, the mailing list in #49, the email queue in #152, the dead-link check and the Internet Archive in #201) updates `/privacy` and its "Last updated" date in the same PR.   - `infra/acs.bicep` (`acs`): the Email Communication Service, `mail.csadvent.christmas` (tracking off, sender `DoNotReply` shown as "C# Advent") and the Communication Service. The resource is `acs` because the connection string the web app reads is `email`.

An action group emailing those addresses; a stateful log search alert every 15 minutes on Error-level `traces` and `exceptions` in Application Insights. **Only exceptions something logged count** (with a severity): .NET's HttpClient tracing and Npgsql's tracing record every failure's exception on its span with no severity or category, so each site the dead-link check found gone was an alert until that was left out; whatever makes a request decides whether its failure is an error. It also leaves out what EF Core logs before the code can handle an error (#224): its `CommandError` traces (EventId 20102, whose failure is always reported again by what comes after it), and its records of the SqlStates the code expects: a unique violation (23505), and a missing table or column (42P01, 42703), which since #151 only a revision started without its migrations meets (#225). Whatever handles those still alerts if it logs an error: a page's unhandled exception, or a background job's failed run; Postgres metric alerts (storage over 80%, CPU credits under 30, more than 30 connections); and a Service Health alert for Central US and Global with no service filter. It takes the App Insights and Postgres `id` outputs. Change recipients through the secret, never the portal. The runbook says what each alert means; the uptime check on `/health` is external and set up by hand.
- **Email has no key.** The web app has its own identity (`web-identity`, `WithAzureUserAssignedIdentity`) with Communication and Email Service Owner on the Communication Service. Its `email` connection string is just `Endpoint=https://…`, so `EmailRegistration` uses `DefaultAzureCredential`. An `AccessKey` still works if one is ever given.
- **The sending domain links itself.** Azure refuses to connect it to the Communication Service before its Domain, SPF, DKIM and DKIM2 checks pass, which can only happen after the nameserver switch (`docs/deployment.md`). `acs.bicep` reads those states and connects the domain on the first deploy after they all pass.
- **The email service, sending domain and sender are create-only** (`@onlyIfNotExists()` in `acs.bicep`). Re-applying the domain made Azure reset its verification to NotStarted, which disconnected it and stopped all email after every deploy. So changes to those three in the template only reach a new environment; change a live one in the portal.
- **Email sending limits:** 30 emails a minute and 100 an hour, per subscription, shared by everything the site sends (the custom-domain default). The organizers decided not to ask Azure for more (#136), so the email queue (Email Queue, above) keeps the whole site under them with `Email:Queue` (25 a minute, 90 an hour, list mail while the hour's under 50). If the limits ever change, update the runbook's Email Sending Limits section, this, and `Email:Queue` together.
- **Database authentication is a password, in publish mode only**, through `pg-admin-username` and `pg-admin-password`. Entra ID would break the migration bundle, and applying it locally would change the container's user and lock out the existing volume. The connection strings live in an Aspire-created Key Vault.
- **PostgreSQL 18 in Azure** needs `ResourceVersion = "2025-08-01"`, because the provisioning default only allows up to 16.
- **Sizing for December (#158):** each replica's connection pool stops at 8 (`connectionsPerReplica` in `AppHost.cs`), passed in publish mode as `Database:MaxPoolSize` and applied by `ConnectionPool` to the connection string every DbContext uses, so the health check, data protection and the email queue's advisory lock share it (there's no other `NpgsqlDataSource`). B1ms leaves 35 connections for us, and the server ran out on October 24-25. Azure's patching has a custom window, Sundays from 08:00 UTC (3 AM Eastern in winter). `Web:MinReplicas` is 1, and 2 from December 1 to 26: the runbook's December and After Advent sections change it in a pull request, never in the portal.
- **Restoring:** 35-day point-in-time backups (`BackupRetentionDays`, Azure's most, raised from 14 for #182; backup storage up to the server's 32 GB is free), Central US only. The privacy page says deleted data can stay in backups 35 days, so change both together. A restore always makes a new server; tested on 2026-10-25, it took about 7 minutes (#90). The steps are in `docs/runbook.md`. Never point the site at a restored server, because the AppHost owns the server's name. Copy the data back instead.
- **Migrations** run as a manually triggered Container Apps job (`migrations`) built from the EF bundle on `mcr.microsoft.com/dotnet/aspnet:11.0.0-rc.2`, pinned by digest to the runtime of `global.json`'s SDK (#180). The bundle runs `UseSeeding` too, so a new database gets the history.
  - **`aspire deploy` runs it before it updates the web app** (#151, `MigrateFirst.cs` in the AppHost). Left to itself, Aspire provisions the job and the web app side by side and never starts the job. The `run-migrations` pipeline step comes after `provision-migrations-containerapp` (the job, with the new bundle's image) and before `provision-web-containerapp` (the only step that changes the web app). It starts the job through Azure Resource Manager with the deploy's own credential (`ContainerAppJobRunner`: the same `start` and execution calls as `az containerapp job start`, the job's resource ID from its Bicep `id` output), and waits up to 10 minutes for it to succeed. If it fails or runs out of time, Aspire skips the steps after it: the web app isn't updated, and the old revision keeps serving.
  - **Aspire's pipeline API is experimental** (`ASPIREPIPELINES001`). `MigrateFirst.Wire` finds the two provisioning steps by their resources' deployment targets and the `provision-infra` tag, and throws if they're missing (an Aspire update that changes them fails CI's publish check, not a deploy). Before the AppHost has prepared its container apps (as it starts, and for `--list-steps`) there's nothing to order, so it changes nothing, and `--list-steps` shows `run-migrations` with no dependencies. `aspire do diagnostics --environment PublishCheck` prints the real order offline. `MigrateFirstTests` (in the integration tests, with no AppHost) cover the wiring and the job runner.
  - **A readiness check can't do this instead** (a "no pending migrations" check on `/health`): Azure only finishes deploying a container app once its new revision is ready (startup and readiness probes passed; a revision that never gets there fails with "Operation expired"), and Aspire waits for that before any later step, so the job would never run.
  - **By hand**, `aspire deploy` runs the step too. Anything else that changes the web app's image (`az containerapp update`, rolling back to an image) runs no migrations.
- **Health checks and probes:** `/health` (every check, the database included) and `/alive` (only the app itself) answer in every environment, first in the pipeline (`UseDefaultHealthChecks`), because a redirect to HTTPS or the canonical host would count as healthy to a probe. They say only Healthy, Degraded or Unhealthy. The web container has Container Apps probes (`PublishAsAzureContainerApp` in `AppHost.cs`): startup and readiness ask `/health`, so a revision that can't reach the database never takes traffic, and liveness asks `/alive`, so a database outage doesn't restart every replica. `/health` is **Degraded** (still a 200, so the probes take no notice) when one of the replica's background job steps is late (`JobsHealthCheck`, see Background Jobs). **Never make a check Unhealthy for anything but the database**: readiness would take every replica out of service.
- **Data protection keys** are in Postgres (`data_protection_keys`, `Data/DataProtectionKeys.cs`), so cookies, antiforgery tokens and email links survive restarts and work across replicas. **In production each key is encrypted at rest with a Key Vault key** (#193, `ProtectKeysWithAzureKeyVault`), so a copy of the database can't mint an organizer's cookie or an unsubscribe link:
  - `infra/dataprotection.bicep` (`dataprotection`, publish mode only) makes the RSA key `data-protection` in `postgres-kv` (the Key Vault Aspire used to add by itself for the connection strings, now added by name in `AppHost.cs` so the template can use it; the same vault in Azure) and gives `web-identity` **Key Vault Crypto Service Encryption User on that key only**. Its versionless URL reaches the web app as `DataProtection:KeyVaultKeyId`, which is **required outside Development** (`ValidateOnStart`); locally and in the tests the keys stay unencrypted. The key API only ever creates the key, so a deploy never changes it. **Never delete it** (the runbook says how to recover one).
  - `DataProtectionKeyCheck` is the first hosted service: it wraps and unwraps with the key (trying for 75 seconds while a new role assignment reaches Key Vault), and **the app doesn't start if it can't**, so a missing key or role fails the deploy (Azure only finishes updating the web app once its new revision is ready, and the workflow's "Check the new revision is serving" makes sure) instead of minting keys other replicas can't read.
  - **Keys from before #193 stay readable**: data protection only decrypts the keys stored encrypted. So nobody is signed out and no link in an email breaks. `EncryptedKeys.EnsureNextKeyIsEncrypted` (from the check) makes an encrypted key that takes over two days later, unless one is current or on its way, so new cookies and links use it without waiting for the old key to expire. The old keys can still unprotect (and so forge) until they're revoked: the runbook's After Advent section revokes them once their unsubscribe links are past 30 days.
- `aspire publish --output-path <dir> --environment PublishCheck` generates the Bicep offline. Check it (and test the bundle image against a throwaway Postgres) after changing the app model. **Never publish test runs in the Production environment**: publish and deploy share saved state (`~/.aspire/deployments/`), and a later `aspire deploy` silently reuses its parameter values and region.
- **Custom domains** are `CustomDomains` in the AppHost's `appsettings.json` (name, then managed certificate name), applied with `ConfigureCustomDomain`. Each domain goes in two steps, because Azure needs DNS pointing at the app before it accepts the domain or issues a certificate. While a certificate name is empty, the domain is HTTP only (`bindingType: Disabled`). `docs/deployment.md` has the cutover steps. **Never bind domains by hand**: every deploy replaces what isn't in the model.
- **Canonical host:** the web app redirects `www.` plus `Site:BaseUrl`'s host to that host, keeping the path and query (`SiteRedirects.UseCanonicalHost`). Legacy addresses redirect too (`SiteRedirects.MapLegacyRedirects`): `/contributor` goes to `/my-spots`, `/mailinglist` to `/announcements`, the old preview image (`/images/csadventSocialCard.png`) and logo (`/images/csadvent logo.png`) to today's, all permanently, and `/substitute` to the current season's `/backups/{year}` (or home when there isn't one).
- **Security headers** (#165, `Content/SecurityHeaders.cs`): set as each response starts, first in the pipeline after the health checks, so redirects (the www one included), error pages and static files get them too.
  - **HSTS** for a year with `includeSubDomains`, outside Development and only over https. Browsers keep it for the year, so it's hard to undo; `preload` would be a separate decision.
  - **http:** the ingress passes plain http on (`AllowInsecure` in `AppHost.cs`), and the app redirects it (301): `http://www.` goes straight to `https://csadvent.christmas` (`UseCanonicalHost`), and the rest to https on port 443 (`UseHttpsRedirection`, configured outside Development only, so the tests' plain http keeps working).
  - **Content-Security-Policy:** scripts only from the site (`App.razor` loads `js/copy.js` and `js/countdown.js`, and no Blazor script since #185), plus inline scripts by SHA-256 hash: the hashes of the import maps `<ImportMap />` would render, worked out from the endpoints' `ImportMapDefinition` when the first response starts, so the policy stays right if `App.razor` ever loads Blazor's script and import map again. Any other inline script, inline event handler or `javascript:` link is refused; put scripts in `wwwroot/js`. `SecurityHeaderTests` checks every inline script on the main pages against the policy. Styles may be inline (the charts, emails); images only come from the site, so visitors' browsers never ask anyone else (the About page's photos are served here, #168), except on the organizers' pages (`/manage`, `SecurityHeaders.OrganizerPages`), which show GitHub's avatars, so a Markdown image from another site won't show; connections can go to any https site, because Blazor's enhanced navigation, if it's ever back, fetches same-site links that redirect elsewhere (`/go`, `/signin`), and a blocked redirect would make the click do nothing; forms may post to GitHub (a post after the sign-in ran out).
  - **Permissions-Policy** turns off the camera, microphone, location, payment and similar features, but not the clipboard (Copy buttons). Only feature names browsers recognize, because Chrome logs an error for any other.
  - **Framing** only by the site itself: `frame-ancestors 'self'`, and `X-Frame-Options: SAMEORIGIN` for older browsers.
  - **No `Server` header** (Kestrel's `AddServerHeader`).
- **Deploying from CI:** `.github/workflows/deploy.yml` runs after CI passes on a push to `main` (`workflow_run`), or by hand (`workflow_dispatch`). It signs in with OIDC (`azure/login`) as the managed identity `id-csadvent-github` (resource group `rg-csadvent-github`, Owner on the subscription), which only trusts the `production` environment. Its federated credential (`github-production-csadvent-ids`) has the owner's and repository's names with their IDs (`repo:CSAdvent@348828352/csadvent.christmas@1427380667:environment:production`), because that's the form GitHub's tokens use here: the name-only form fails with AADSTS700213. **Renaming or transferring the repository changes it** (it moved from CodingWithCalvin/CSAdvent on 2026-10-27): add a credential for the new subject first (the runbook's Azure Sign-In for GitHub Actions). That environment is limited to `main` and holds the variables and the two secrets (`docs/deployment.md`). The workflow runs `aspire deploy --non-interactive` with the parameters as `Parameters__{name}` environment variables (it runs the migrations before it updates the web app, and fails if they do), then checks the site, and that the new revision is the one serving (`latestRevisionName` equals `latestReadyRevisionName`), because a revision that can't start leaves the old one answering. For a commit from before #151, whose AppHost has no `run-migrations` step (a rollback; the workflow checks for `MigrateFirst.cs`), it starts the migrations job after the deploy, as it used to. **Only `main`'s latest code deploys** (#179): its first step skips a `workflow_run` whose commit `main` has moved on from (unless only documentation changed since), and **Run workflow** takes a `sha` to redeploy an earlier commit of `main` (the runbook's Rolling Back a Deploy). Its actions are pinned to commit SHAs with the tag in a comment, and `az extension add --name containerapp` to a version (#180).
- **CI** (#177, #178): every workflow runs on `ubuntu-24.04`, pinned through the season. `ci.yml` and `deploy.yml` install only `global.json`'s SDK, with `dotnet-install.sh` from a pinned commit of dotnet/install-scripts (`setup-dotnet` always adds the latest LTS runtime too). On pull requests, CI checks the Azure publish: `aspire do publish-azure-environment --environment PublishCheck` (`aspire publish` without the slow migration bundle), with placeholder parameters so the optional parts are generated, then `bicep build`. A failing test run uploads a TRX file (`--report-xunit-trx`). `AppHostFixture` filters the relayed resource logs (`CSAdvent.AppHost.Resources`) to warnings, one line of output each, and the web app's own warnings and errors come through (#248, see Gotchas). The Aspire CLI version is in both workflows. **Dependabot** (`.github/dependabot.yml`) opens one grouped pull request a week per ecosystem (NuGet, actions), ignoring EF Core, Npgsql, Aspire and AngleSharp until #55, and is paused in December.
- **Actions minutes** (#140): the repository is public (since 2026-10-26), so standard runners cost nothing. Still, `ci.yml` cancels a pull request's superseded runs, and skips documentation-only changes (`README.md`, `CLAUDE.md`, `docs/`): `paths-ignore` on pushes to `main`, so they don't deploy either, and a "Check for code changes" step on pull requests, so "Build and test" still passes and can't hold up a required check. Keep the two lists in step, and the third in `deploy.yml`'s "Choose the commit".
- **Migrations run before the new revision starts** (#151), so new code never meets an older schema. **Each migration must still work with the code before it**: the old revision serves while the job runs, and goes on serving if a later step fails, and a rollback runs older code on the newer schema. So add first, and remove in a later release. **No migrations from December 1 to 26** (the runbook's schema freeze). The #225 handling (a background job that finds a table or column missing logs a warning) stays, for a revision started without its migrations.
- **Aspire's Azure sign-in** is `Azure:CredentialSource` (`AzureCli`). `Azure:CredentialProcessTimeoutSeconds` raises the roughly 10-second limit on `az` handing out a token, which can run out while images build.

## Data Model

Entities and their EF configuration live together in `src/CSAdvent.Web/Data` (one file each).

- **Seasons are keyed by year** and hold every season since 2017. `slots_per_day` is 1 for 2017 and 2 since. `Season.Create` adds an open slot for every day and part; creating a season never touches earlier ones.
- **No stored status.** A slot is open or claimed depending on whether it has an author. Reveal times are computed by `Calendar/AdventSchedule` from the year, the day and `Advent:TimeZone` (midnight in that zone), never stored. Claims open at `seasons.claims_open_at`.
- **A spot's author** (#188, #245): whatever gives a spot an author (approving a request, an organizer filling it in the entry editor, a backup taking it) clears `dropped_out_at`, so a spot with an author is never dropped out (`ck_slots_author_not_dropped_out`), and a spot without an author is nobody's (`ck_slots_contributor_needs_author`). My spots, profiles and author renames only change spots that already have an author. The drop-out rule came a release after #188, because the code before #188 broke it and kept serving while the migrations ran (and would come back with a rollback); its migration (`AddAuthorNotDroppedOutCheck`) clears the rows it would refuse first. `announcements.season_year` is a foreign key to `seasons`.
- **A season ends twice** (#146), so pick the one you mean on `AdventSchedule`: `IsLastDayRevealed` (midnight on December 25: the archive, the sitemap, the season card, an entry page's calendar link) and `IsFinished` (the end of December 25: My spots, history, post claims and links, authors, retrospectives, past author invitations, the backup list and the organizers' current season). Both follow a rehearsal.
- **Public vs private:** `slots` is public and never holds an email. Contact details live in `slot_contacts`, `contributors`, `claim_requests` and `substitutes`, so they never show on the calendar, and requests and backup lists can be purged after a season without touching it.
- **snake_case names** come from `SnakeCaseNamingConvention`, so raw SQL in check constraints and filters uses snake_case column names.
- **Concurrency:** `slots` and `claim_requests` use PostgreSQL `xmin` as a row version.
- **Expected database errors** are named in catch filters: `catch (DbUpdateException exception) when (exception.IsUniqueViolation())`, or `IsForeignKeyViolation()` (`Data/DatabaseErrors`). `ExecuteUpdate` and `ExecuteDelete` throw the `PostgresException` itself, so theirs is `catch (PostgresException exception) when (exception.IsUniqueViolation())`.
- **Unit tests fail if the model changes without a migration** (`HasPendingModelChanges`).
- **History** is in `Data/Archive/{year}.json` (2017-2025 from the legacy site, then each finished season), embedded in the web assembly and seeded by `ArchiveSeeder` through EF Core's `UseSeeding`, which runs after every migration (`dotnet ef database update`, the Aspire migrations step, and the migration bundle). It only adds seasons that are missing, so **editing the JSON doesn't change a database that's already seeded**. Locally, use **Reset Database** on the `migrations` resource to reseed.
  - **Exporting a season** (#182): each finished season's file is downloaded from `/manage/seasons` (`SeasonArchiveExport`, `/manage/seasons/{year}/archive.json`, Admin policy; never the test season or a season that isn't over) and committed in January (runbook). It's the calendar as shown, `postSummary` included (`ArchivedSlot`), with no contact details or accounts, written by `ArchiveSeeder.Serialize` exactly like the existing files (`ArchiveSeederTests` checks). Taking an entry down means editing its file too.
  - **No scheduled logical backup** (`pg_dump` to Blob Storage, the rest of #182), decided 2026-10-26: it would need a storage account, a scheduled job with an image of its own, credentials and a restore nobody has tried, for two volunteers, and it would keep deleted emails longer than the privacy page says. Instead the point-in-time backups went from 14 to 35 days (Hosting, Restoring), and with these files they cover what matters. The runbook's Restoring the Database has the plan for an off-server copy if that's ever wanted.

## Gotchas

- **AngleSharp is pinned to bUnit's version** (1.8.5). Central transitive pinning gives the unit tests the web app's version too, and AngleSharp 1.8.6 breaks bUnit 2.12.5 (`TypeLoadException` in every component test). Update them together.
- **User secrets are shared with the tests:** the AppHost's generated Postgres password is saved in its user secrets, and the local data volume is created with it. The test fixture passes a fixed `Parameters:postgres-password` so test runs never overwrite that secret. If local Postgres rejects the password, delete the `*-postgres-data` Docker volume and run again.
- **Don't call `CreateResourceBuilder(web).WithEnvironment(...)` in the test fixture.** It makes Aspire drop the web project's launch profile environment, so the app runs as Production. Put test-only settings in the AppHost's `isTesting` branch instead.
- **EF Core logs a failed command at Error before any catch block runs** (`CommandError`, then `SaveChangesFailed` or a failed query), so catching an expected database error doesn't keep it out of the logs. Don't insert a record on every run for the unique index to refuse: load what's recorded and skip it, keeping the index as the guard against two runs at once (#157). The error alert leaves out EF Core's and Npgsql's records of a unique violation (#224). `ExpectedErrorTests` (seasons 2400-2419) make inserting a record that's already there fail outright, with triggers only the test database gets, so a run that stops skipping fails them.
- **Background jobs can meet an older schema** (#225): deploys run the migrations first (#151), but a revision started without them (an image changed by hand) runs new code on the old schema. `PeriodicWorker` catches `MissingSchema.IsMissingTableOrColumn` (SqlState 42P01 or 42703, anywhere in the inner exceptions) for each step before its general catch, and logs a Warning instead of an Error; the next run works once the migrations are in. A new worker gets that by deriving from `PeriodicWorker`; one that can't (the email queue's) needs the same catch (`ExpectedErrorTests` runs the retention worker against a database without the tables). `EachSpot` lets it through rather than log it per spot. Use `MissingSchema.IsMissingTable` where only a missing table can be taken as empty (the do-not-email list).
- **SQL statements aren't logged:** `Microsoft.EntityFrameworkCore.Database.Command` is at Warning in `appsettings.json` (#157). At Information every statement went to Application Insights, a few every 2 seconds from the email queue's worker alone on each replica. Each command is still a `postgresql` dependency there, from Npgsql's tracing.
- **Minimal API POST endpoints don't enforce antiforgery unless they bind form data.** Call `IAntiforgery.IsRequestValidAsync` explicitly, as `/signout` does.
- **Testing environment:** the integration tests start the AppHost with `--environment=Testing`. In that environment the AppHost drops the Postgres data volume and pgweb, and runs the web project's `http` launch profile so tests don't need a trusted dev certificate. Keep that branch in `AppHost.cs` when changing resources.
- **The web app's logs in the test output** (#248): the AppHost relays each line of a resource's console as a log of its own (`CSAdvent.AppHost.Resources.{resource}`, message `{line}: {timestamp} {text}`), standard output as Information and standard error as Error, and `AppHostFixture` keeps only Warning and up. So in the Testing environment the web app's console logger writes Warning and up to standard error (`Logging:Console:LogToStandardErrorThreshold`), without colors, and leaves out EF Core's failed commands' SQL (`Microsoft.EntityFrameworkCore.Database.Command`, set with `WithArgs`: an environment variable with dots in its name never reached the web app on CI's Linux runner). They show as `fail: CSAdvent.AppHost.Resources.web[0]` whatever their level, with the web app's own `warn:` or `fail:` in the line, and an exception's stack trace a line at a time. Its Information logs never reach the output.
- **Starting the AppHost in the tests** (`AppHostFixture`) takes under two minutes on a quiet machine, most of it the migrations step (dotnet-ef evaluates the web project with MSBuild before applying anything). With several runs at once it has taken far longer: Docker too slow for DCP's health checks ("RuntimeUnhealthy"), or DCP unable to update the web app's status. So it gets 12 minutes, a first attempt that fails or takes 7 is abandoned for a fresh one, and a timeout says where each resource got to. The tests' database connections (`fixture.GetConnectionStringAsync`) allow 60 seconds to connect, and `CreateWebClient` never sends a POST twice (a run that timed out may have finished).
- **EF Core 11 with Aspire 13.6:** `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` has no `net11.0` build yet. We reference `Npgsql.EntityFrameworkCore.PostgreSQL` 11.x directly and pin the EF Core health-check package transitively, so everything resolves to EF Core 11.
- **dotnet-ef version** is pinned twice: `dotnet-tools.json` and `WithToolVersion` in `AppHost.cs`. Update both together.
- **EF Core 11 refuses to run `database update` with no migrations**, which is why there's an empty `InitialCreate` baseline.
- **`dotnet ef migrations remove` needs a database connection**, which only exists inside Aspire. Use **Remove Migration** on the `migrations` resource in the dashboard, or delete the migration's two files and restore `AdventDbContextModelSnapshot.cs` from git.
- **`Aspire.Hosting.EntityFrameworkCore` is preview-only**, and logs a harmless `Could not perform substitution for environment variable ASPNETCORE_URLS` error when its tool process starts.
- **AspireUseCliBundle is false** on purpose, so the AppHost works with `dotnet run`, IDEs, CI, and `Aspire.Hosting.Testing` without the Aspire CLI. ASPIRE010 is suppressed for that reason.
- **Blazor's form binding sets a list property to null** when a post has none of its fields, whatever its initializer. A form model with a list (`PostLinksForm.Posts`) turns null into an empty list in its setter.
- **A page renders only one `HeadContent`** (the last one wins). `SocialMeta` owns it on public pages, so put any other head tags in its child content.
- **`.gitignore` used to ignore every `Backup*/` folder** (a Visual Studio template rule), which hid the app's `Backups` folders from git. It's now root-only (`/Backup*/`). If new files seem to vanish from `git status`, check `git check-ignore -v <path>`.
- **When .NET 11 reaches GA:** update `global.json`, the EF Core, Npgsql, and Aspire packages, `dotnet-ef` (both places), and container base images (the migrations job's tag and digest in `AppHost.cs`), then drop those packages from Dependabot's `ignore`.
