# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Critical Rules

**These rules override all other instructions:**

1. **NEVER commit directly to main** - Always create a feature branch and submit a pull request
2. **Conventional commits** - Format: `type(scope): description`
3. **GitHub Issues for TODOs** - Use `gh` CLI to manage issues, no local TODO files. Use conventional commit format for issue titles
4. **Pull Request titles** - Use conventional commit format (same as commits)
5. **Branch naming** - Use format: `type/scope/short-description` (e.g., `feat/calendar/countdown`)
6. **Working an issue** - Always create a new branch from an updated main branch
7. **Check branch status before pushing** - Verify the remote tracking branch still exists. If a PR was merged/deleted, create a new branch from main instead
8. **Write tests** - All new/refactored code requires tests where applicable
9. **Run validation before commits** - Run `dotnet build` and `dotnet test` and verify no errors before committing
10. **No co-authors** - Do not add co-author information on commits or pull requests
11. **No "generated by" statements** - Do not add generated-by statements on pull requests

## Project Overview

- **The yearly cycle** is in `docs/runbook.md`. Keep it current when a change affects what organizers do, or when something happens, during the season.

The new C# Advent site (csadvent.christmas), replacing the legacy site Matt Groves built. The pinned tracker issue (#52) lists every piece of work. The legacy code is a feature spec only; nothing is ported from it directly.

- **.NET 11** Blazor Web App (RC with a go-live license until GA in November 2026)
- **PostgreSQL** holds every season, archives included. Archive pages render from the database, never from static pages.
- **Aspire** orchestrates local development, telemetry, and deployment

## Commands


## Architecture

| Project | Role |
|---|---|
| `src/CSAdvent.AppHost` | Aspire app model |
| `src/CSAdvent.ServiceDefaults` | OpenTelemetry, health checks, resilience, service discovery |
| `src/CSAdvent.Web` | Blazor Web App; `Data/AdventDbContext.cs` and `Data/Migrations` |
| `tests/CSAdvent.UnitTests` | xUnit v3 on Microsoft.Testing.Platform; no database or containers |
| `tests/CSAdvent.IntegrationTests` | Starts the AppHost via `Aspire.Hosting.Testing`; web and database tests |

- **Package versions** are central in `Directory.Packages.props`. Target framework, nullable, and warnings-as-errors are in `Directory.Build.props`.
- **Render modes:** pages are static server-rendered by default. Add `@rendermode InteractiveServer` only to components that need it (forms, admin, countdown).
- **Migrations** run through Aspire's EF Core migrations integration (`AddEFMigrations` with `RunDatabaseUpdateOnStart`), never at app startup. Publishing produces a migration bundle.

## Styling

- **Tailwind CSS 4**, built by `build/Tailwind.targets` during `dotnet build`. It downloads the official standalone CLI into `.tools/` (gitignored, checked against a pinned SHA-256) and turns `src/CSAdvent.Web/Styles/app.css` into `wwwroot/app.css` (gitignored and generated, so never edit it).
- Tailwind only scans `src/CSAdvent.Web/Components` (`@source` in `Styles/app.css`). Write class names out in full in the Razor markup, because classes assembled from strings at runtime are never generated.
- Brand colors are the `advent-*` scale in `@theme`: `advent-600` (`#1a509d`) is the logo blue and `advent-400` (`#4e88c5`) the snowflake. Don't put `advent-400` behind body text, because its contrast on white is too low.
- Photos live in `wwwroot/images` as WebP with a JPEG fallback, through the `bg-advent-candles` and `bg-advent-snowflakes` utilities.
- Pages render statically on the server. `CalendarGrid` renders a season's days for the home page and the archive. `CalendarEntry` never carries a post's title or link before its reveal.
- **Countdown (#31):** the day revealed next counts down ("Revealed in 11:42:07") once it's within 24 hours (`SeasonCalendar.CountingDownTo`, from `GeneratedAt`). `wwwroot/js/countdown.js` ticks it, correcting the visitor's clock with the server's time (`data-now`), and reloads once at the reveal, a few seconds late and spread out. It follows the rehearsal in the test season.
- **Home page** (`HomeService.Plan`): a season's calendar is shown from when its sign-ups open (or December 1, if that's sooner or sign-ups aren't scheduled) **until the end of December** (`AdventSchedule.IsCalendarShown`), earliest season first, so creating next year's season early never replaces this year's. Once every day is revealed, `CurrentSeason` says "That's a wrap" instead of counting spots.
- **Between seasons** the home page is `OffSeason`: thanks for the latest finished season (posts and authors), the organizers' `between-seasons` content block, when the next season's sign-ups open (if the season exists and is scheduled), and the archive. From **September 1** (`HomeService.CountdownFrom`) it counts down the days ("33 days until sign-ups open!"). It's server-rendered, so there's no script.
- Organizer pages work on the **current season** (`SeasonAdminService.GetCurrentYearAsync`): the earliest season whose last day isn't over. **When every season is finished there's no current season**, and Requests, Entries, Backups, Social and Other Advents show `NoCurrentSeason` rather than last year's data. Past seasons are opened from the overview's **Past seasons** list (`?year=`), where `PastSeasonNotice` says they're history. A finished season's sign-ups can't be edited.
- Component tests use **bUnit** (`BunitContext`) in `tests/CSAdvent.UnitTests`. `CalendarFixtures` builds a season as seen on a given date with a fake clock.

## Sign-in

- **Cookie sessions, with GitHub OAuth** through ASP.NET Core's built-in `AddOAuth` (`Auth/AccountEndpoints.cs`), not a third-party provider. Signing in calls `/user/emails` and keeps only a **primary, verified** address, then upserts the contributor by GitHub user ID (`ContributorSignIn`).
- **Claims:** GitHub user ID (`NameIdentifier`), login (`Name`), verified email, the GitHub profile name (`csadvent:github_name`, if set) and `csadvent:contributor_id`. Use `User.GetContributorId()` to scope a contributor to their own data, and `User.GetDisplayName()` for the profile name with the login as a fallback.
- **Organizers** are GitHub user IDs in `Accounts:Admins`: CalvinAllen (`41448698`) and mgroves (`103484`). Use the `AdventPolicies.Admin` policy (for example `@attribute [Authorize(Policy = AdventPolicies.Admin)]`), which is checked on every request.
- **Dev sign-in** (`/dev/signin?login=...&id=...`) is mapped only when the environment is Development **and** `Accounts:DevSignIn` is true, which the AppHost sets in run mode. The integration tests use it, with organizer `9001` set by the AppHost in the Testing environment.
- **GitHub settings** come from the AppHost parameters `github-client-id` and `github-client-secret`. They're optional locally and required in production; the app fails to start without them outside Development.

## Claims

- `/claim/{year}/{day}/{part}` (`CalendarLinks.Claim`) requires sign-in. `ClaimService.CheckAvailability` decides whether a slot can be requested: claims are open, the day isn't revealed, and nobody has claimed it. It's checked again on submit.
- A request is stored as `Pending` with the contributor's **verified GitHub email** (there's no typed-in email). Requests don't reserve the slot; the organizer approves one. A duplicate pending request from the same contributor hits the unique index and is reported as already requested.
- **Social accounts** (Bluesky, Mastodon, LinkedIn, Facebook, Reddit, X) are optional fields on the claim form. They're saved on `contributors` with the name and link (`display_name`, `website_url`), so they're on the contributor's profile and prefilled next time, used to tag people in social posts (#59), and linked from their entry pages. `SocialAccounts.TryNormalize` accepts handles or profile URLs and stores one form per platform.
- **The name link is a website or blog.** Every form a contributor fills in (claim, profile, My spots, backup sign-up and offer) refuses social media profiles there (`[NotSocialProfile]`, `SocialAccounts.IsSocialProfile`: the big networks by host, and any `https://{server}/@user` as Mastodon, except Medium, Substack and YouTube). Organizer forms don't check it, because archive posts keep the links they were published with, Twitter included.
- **Without a website, the name links to the author's GitHub profile** (`AuthorLinks.ForName`, from the slot's contributor), on the calendar, the archive and the entry page. Calendar queries include `Slot.Contributor` for this.
- New requests and approvals go to `IClaimNotifier` (`EmailClaimNotifier`). It emails the contributor, and for new requests the organizers too, with replies going to the contributor. A failed send is logged without personal details and never blocks the claim.
- Blazor SSR forms: `[SupplyParameterFromForm(FormName = ...)]` on a nullable model, `Form ??= new()` to tell a GET from a POST, and `@bind-Value="Form!.Field"`. The posted field names are `Form.Field`.

## My Spots

- `/my-spots` (`MySpotsService`) is where contributors manage their own spots in seasons that aren't over: add their post's title and URL (**the only way posts get onto the calendar**; nobody sends details by replying to an email), fix their name and link, and see pending requests.
- A spot is theirs if `slots.contributor_id` is them, or if it isn't linked to anyone and its contact email is their verified GitHub email (spots an organizer added by hand). Saving links it. Anyone else's spot is a 404.
- The title and URL go together, because the calendar links the title to the post. Edits post the spot's `xmin` version back, so an organizer's edit in between isn't overwritten.
- **Dropping out** (until the day is over) clears the author, link, post, contributor and contact, so they're never named, sets `slots.dropped_out_at`, and emails the organizers. An organizer releasing a spot in the entry editor sets `dropped_out_at` too. A dropped-out spot that's still open is what the backup posters get asked about (#36).
- Emails link to `ClaimEmails.MySpots(site)`.
- **History:** My spots also lists every post linked to the contributor (`slots.contributor_id`) in seasons that are over, as "Your C# Advent history" (`MySpotsService.GetHistoryAsync`). Organizers see "Returning · N posts" on that person's requests.
- **Asking for older posts** (#120, `PostClaimService`, `post_claim_requests`): a signed-in contributor can ask for a finished season's post that isn't on anyone's account to be added to theirs, at `/my-spots/claim/{year}/{day}/{part}` (`PostClaimLinks.Claim`).
  - **Finding them:** a finished-season entry page without an account links there ("Did you write this post?"), and My spots has **Wrote for C# Advent before?**: a search by author name (`?find=`, `ILIKE` with `EscapeLike`, up to 50, prefilled with their name), plus their requests still waiting.
  - **Asking:** they tick "I wrote this post" and can add a note. Every request emails the organizers (`PostClaimEmails.NewRequest`, replies to the requester). It needs a verified GitHub email, is limited to `MaxPerHour` (10) per person, and one pending request per person and post (a filtered unique index). Never the test season, and never a season that isn't over.
  - **Reviewing:** organizers review at `/manage/authors/requests` (linked from Authors with the count) and `/manage/authors/requests/{id}`. Approving sets the slot's `contributor_id`, guarded by both rows' `xmin`, and can also link their other unlinked posts under the same name (`AuthorService.CombineAsync`). A post that's on someone else's account by then can't be approved. The requester is emailed either way (`Approved`, `Declined`).
  - **Already on someone's account:** the post can't be requested. The claim page, My spots and the privacy page say to email `Site:ContactEmail` if it's theirs.
  - **Retention:** requests keep no email address. A decided one is deleted 30 days later by `ContactRetention` (`PostClaimsKeptFor`), and the privacy page says so.
- **New links for older posts** (`PostLinkService`, `post_link_requests` with `post_link_changes`): for an author who moved their blog or a post. Posts in a season that isn't over are edited on My spots instead.
  - **Asking:** `/my-spots/links` (`PostLinkLinks.Request`, linked under their history) lists every post on their account from finished seasons with its link in a field (`PostLinksForm`, `Form.Posts[i].Url` with a hidden `SlotId`). Whatever they change is **one request**, however many posts (`PostLinkService.Changes`: only their own posts, only links that differ), with an optional note. It emails the organizers once (`PostLinkEmails.NewRequest`, replies to the requester), needs a verified GitHub email, and is limited to `MaxPerHour` (5) per person.
  - **One at a time:** each person has at most one pending request (a filtered unique index). While it's waiting the page shows it with **Withdraw** (status `Withdrawn`), so they can fix a typo and ask again.
  - **Reviewing:** organizers review at `/manage/authors/link-changes` (linked from Authors with the count) and `/manage/authors/link-changes/{id}`, which shows each post's old and new link. **Approve** changes every link in the request (guarded by the request's `xmin`), and is refused if a post isn't on the requester's account any more; **Decline** changes nothing. The requester is emailed either way (`Approved`, `Declined`, transactional). Each change keeps the old link, so a bad approval can be undone in the entry editor.
  - **Organizers directly:** `/manage/authors/{id}/links` and `/manage/authors/unlinked/links?key=` (`AuthorPostLinks`, linked from both author pages) change an author's links without a request, any season, each guarded by its spot's `xmin`.
  - **Where it shows:** the calendar, the archive, entry pages and every link we've published since 2026 go through `/go`, so a new link applies to all of them at once. Links the old site published went straight to the post.
  - **Retention:** like post claims, no email address is kept, and a decided or withdrawn request is deleted 30 days later (`PostLinkRequestsKeptFor`).
- **How their posts did:** each revealed spot and history post shows its visits and clicks (`PostTraffic`, from `entry_hits`, all time). Only the author sees their own; the public only sees a season's totals and its ten most-read posts in the retrospective.
- **Profile** (`/profile`, `ProfileService`, linked from the account menu): the name and link a contributor wants on the calendar, and their social accounts, with the same limits as the claim form (`ProfileForm`). It fills in their next claim, and a claim updates it. "Also show this on my spots" puts the name and link on every spot of theirs, past seasons included. Their GitHub login and verified email are shown read-only, because they come from GitHub.
- **Social accounts from GitHub:** on a contributor's first GitHub sign-in, `GitHubSignIn` calls `ProfileService.FillInFromGitHubOnceAsync`, which reads the social links on their public GitHub profile (`GitHubUsers.SocialAccountsAsync`) and fills in their **empty** account fields (`SocialAccounts.FromGitHub`: Mastodon by GitHub's provider, the rest by address, X on `x.com` or `twitter.com`; LinkedIn company pages are skipped). `contributors.github_social_checked_at` makes it once, so an account they remove doesn't come back; **Fill in from GitHub** on `/profile` runs it again on request. GitHub gets 5 seconds (`ProfileService.GitHubTimeout`), and if it fails the sign-in carries on and it's tried next time. Dev sign-in never calls GitHub, so the tests don't either.
- **Authors** (`/manage/authors`, `AuthorService`): every author in every season. Linked people are one row each, whatever names they've used; archive authors who aren't linked yet are grouped by name whatever its case or spacing (`AuthorService.Key`). Each season links to the post.
  - **Linking:** an organizer links an archive author to a GitHub login, which sets `contributor_id` on every finished-season post with that name. Someone who hasn't signed in gets a contributor record with only their public GitHub user ID and login, looked up through `GitHubUsers` (with the OAuth app's credentials, for GitHub's higher rate limit). Their first sign-in picks it up, because sign-in upserts by GitHub user ID. Posts from 2026 on are linked when their claim is approved. The privacy page says so.
  - **A linked author's page** (`/manage/authors/{contributorId}`, `AuthorEdit`) edits their profile (the same `ProfileService` as `/profile`), lists their spots with links to the entry editor, and has **Also wrote as**: add an unlinked archive author's posts to them (`CombineAsync`), with names sharing a word with theirs suggested first (`SharesAName`). **Unlink** (confirmed) only unlinks seasons that are over.
  - **An unlinked author's page** (`/manage/authors/unlinked?key=`) links them, or renames them on all their posts. Giving two unlinked authors the same name groups them together.

## Entry Pages and Traffic

- **Every revealed entry with a post has a page** at `/{year}/day/{day}/{part}` (`EntryService`, `EntryLinks.Page`). It shows the title, author, the author's links (`AuthorLinks.All`: website, GitHub, then the social accounts on their profile), a **Read the post** button and the day's other post. Before the reveal it says only when the post is coming (#5), and a revealed spot without a post (or with no title) is a 404.
- **"Read the post" goes through `/go/{year}/{day}/{part}`**, which counts the click and redirects (302) to the entry's own post URL. Nothing else can be a destination, so it isn't an open redirect.
- **Every link we publish goes through us, tagged with `?via=`:**
  - Social posts and RSS link to the entry page (for the preview card).
  - The calendar (`via=calendar`) and the daily email (`via=email`) link straight to `/go`.
  - The entry page's button passes on the tag the visit arrived with (`site` if none).
  - Retrospectives link to their most-read posts' pages with `via=retrospective`.
  - Tags are normalized by `EntryVia` (unknown becomes `other`).
- **Counting:** `entry_hits` records a `View` or `Click` with the slot, time and tag. There's no IP, cookie or user agent, so nothing personal, and the hits are kept for the stats (#62). `EntryTraffic.IsPerson` skips link-preview fetchers (Facebook, LinkedIn, Mastodon, Bluesky, Discord...), crawlers, scripts, prefetches and non-GET requests. The organizers' entries list shows clicks per spot.
- **Preview tags:** `SocialMeta` puts Open Graph tags, `twitter:card` (large image), `twitter:site` (`Social:X`), a canonical URL without the query string, and `fediverse:creator` (`Social:Mastodon`) on every public page.
- **Cards** (`CardRenderer`, SkiaSharp):
  - What they show: a revealed entry's page uses `/cards/{year}/{day}/{part}.jpg` (title, author, day). Season pages use `/cards/{year}.jpg`. The home page (`CardLinks.Home`) uses the season on the calendar, or between seasons the next season's card saying when its sign-ups open (`CardLinks.Upcoming`), and otherwise the general card: **never a finished season's**, which would read as if that Advent were still on. Anything else, including entries before their reveal, uses the static general card `images/social-card.jpg`.
  - Size: 1200×630 JPEGs of about 110 KB, under Bluesky's 1 MB limit.
  - Caching: `CardLinks` adds `?v=` (a hash of the text, or the post count), so an edited title gets a new URL. Responses are cached for a day, and rendered cards are kept in memory.
  - Before an entry's reveal there's no card for it (404).
  - Fonts and images: Inter Bold and Regular (SIL Open Font License, `Cards/Assets/Inter-LICENSE.txt`), the card background and the logo are embedded resources. Linux uses `SkiaSharp.NativeAssets.Linux.NoDependencies`, so containers need no fontconfig or system fonts. `CardRenderer.Printable` drops characters Inter can't draw (emoji, for example) rather than draw boxes.

## Content Pages

- **Content blocks** (`ContentService`, `content_blocks` plus `content_block_revisions`): copy organizers edit at `/manage/content` without a redeploy, in Markdown rendered by `Markdown.ToHtml` (raw HTML escaped, unsafe links dropped) inside `MarkdownBlock`.
  - Each block is defined in `ContentCatalog` with **default copy in code**, shown until the first save, so nothing needs seeding.
  - Every save adds a revision, and any revision can be loaded back into the editor.
  - To add a block, add it to `ContentCatalog` and read it with `ContentService.GetAsync(key)`.
- **`/about`** shows the `about` block (history and rules, from the copy recovered in #2) and the organizers from `Site:Organizers` (name, GitHub login for the photo, and a `Role` line). **Matt Groves is the founder and always a host** (`Founder: true`; Calvin co-founded it, but it's Matt's brainchild): he's featured first, above the history, and everyone else is listed as a co-host below it.
- **`/others`** shows the `other-advents` block and a list kept **per season** in `other_advents` (`OtherAdventsService`): the current season's, else the latest season's, else `OtherAdventsService.Suggestions`.
  - The legacy list was pruned of dead links and one-off calendars.
  - Organizers edit it at `/manage/other-advents`: add, remove, or start the season from last year's list. Remove is a plain form to a minimal API, because there's one per item.
- **Other Advents logos** (`OtherAdventLogoService`, `other_advent_logos`) are kept **by calendar address**, so every season's list and the suggestions share them. `OtherAdventLogoWorker` fetches missing ones every minute, and asks a site without a usable icon again after a day. Organizers can **Refresh** or **Upload** a logo on `/manage/other-advents` (plain forms to minimal APIs, one per calendar).
  - `LogoFetcher` reads the site's home page for `apple-touch-icon` and `icon` links (`LogoFinder`), then tries `/apple-touch-icon.png` and `/favicon.ico`. SVG icons can't be drawn, so those sites need an upload.
  - **Its client only connects to public addresses** (`PublicAddresses.ConnectCallback`, checked on every connection, redirects included), so organizer-typed URLs can't reach the container network or the metadata endpoint. It has its own `HttpClient`, so the default retries don't apply.
  - **Every logo is redrawn** by `LogoImages` (SkiaSharp) into a PNG of at most 128 pixels, refusing anything over 4096 pixels, so only plain images are served from `/others/logos/{id}.png?v=…` (cached for a week, `nosniff`).
  - The AppHost turns the worker off in the Testing environment (`OtherAdvents:FetchLogosInBackground`), so tests never reach real sites.

## Social Announcements

- **C# Advent's own accounts** are in `Social` (`SocialAccountsOptions`):
  - Bluesky `csadvent.christmas`
  - Mastodon `@csadvent@mastodon.social`
  - the Facebook and LinkedIn Pages
  - Reddit `u/CS-Advent`, posting to **r/csadvent** (never r/csharp or r/dotnet)
  - X `@csadvent`

  The footer links them all ("Follow C# Advent"), with `rel="me"` on Mastodon so its profile can verify the site.

- **Every revealed entry with a post gets one announcement per platform:** Bluesky, Mastodon, LinkedIn, Facebook, Reddit and X, using `Claims.SocialPlatform`. The content is the same everywhere (`Announcement`: title, author, "C# Advent 2026, December 6, part 2", and a link to the entry page tagged with the platform). `AnnouncementFormatter` handles each platform's conventions:
  - **Bluesky:** 300 graphemes, `@handle` mentions, and a compose intent.
  - **Mastodon:** 500 characters, where a link counts as 23 and `@user@server` counts as `@user`. The share link opens on `Social:Mastodon`'s server.
  - **LinkedIn:** 3000 characters, a "tag the author" hint, and a composer link (`linkedin.com/feed/?shareActive=true&text=`). LinkedIn doesn't document it (its documented share link only takes a URL), so if the composer opens empty, paste with Copy.
  - **Facebook:** fewer hashtags, and a hint.
  - **Reddit:** a title of up to 300 characters plus the link, no hashtags, and a submit link.
  - **X:** 280, counted X's way (`XLength`): a link is 23, an emoji or "…" is 2, and text X would link, like "ASP.NET", counts as a link. `@username` mentions, and X's documented web intent (`x.com/intent/tweet?text=`).
  - **Long titles** are shortened with an ellipsis to fit.
- **`/manage/social`** (organizers) shows a day's announcements, today by default. Each has a preview, a count against the limit, Copy buttons (`wwwroot/js/copy.js`, `data-copy="element-id"`), and the composer link where one exists. Upcoming days are preview-only, with no composer and no marking before the reveal (#5).
- **Mark as posted / Undo** are plain forms posting to `/manage/social/mark` and `/unmark` (minimal APIs; binding the form checks antiforgery; Admin policy). They're plain because the page has one per entry and platform, and Blazor form names must be unique. They record `social_posts` (unique per slot and platform: status, time, optional post link, and who marked it; `automation` for #61).
- **Automatic posting** (#61, `Social/Posting`): Mastodon, Bluesky, the Facebook Page and X. LinkedIn and Reddit have no API access, so they're always copy and paste.
  - **Modes:** each platform is Automatic, Manual (the default) or Off in `social_platform_settings`, set on `/manage/social` (plain forms to `/manage/social/mode`), so switching takes effect without a redeploy. Off platforms are left off the page. Automatic needs a publisher (`SocialPublishers.For`): credentials, or dry-run mode.
  - **When:** `SocialPostingWorker` runs `SocialPostingService.RunAsync` every 5 minutes. Each entry goes out on its day at `SocialPosting:PostAt` (10 AM for post 1, 2 PM for post 2, Eastern), or as soon as its link arrives (or its blurb check passes) after that, but never once its day has passed. **Never the test season.**
  - **Exactly once:** a run claims an announcement by inserting its `social_posts` row as `Posting` before posting; the unique index means only one run or replica gets it, and anything marked by hand is skipped. A failure is `Failed` with the platform's error, retried after 5, then 10 minutes, up to `SocialPosting:MaxAttempts` (3), then waits for **Retry now** (`/manage/social/retry`). A row still `Posting` after 15 minutes was interrupted, so it's marked failed for an organizer to check, never retried by itself. Mastodon also gets an `Idempotency-Key`.
  - **Publishers** (`ISocialPublisher`, tested with fake HTTP handlers): Mastodon `POST /api/v1/statuses`; Bluesky through XRPC with an app password, marking up links, mentions and hashtags as facets (UTF-8 byte offsets; mentions resolved to DIDs) and building the link card from our share card (`uploadBlob`); Facebook `POST /{page-id}/feed` with the Page token in the Authorization header; X `POST /2/tweets`, signed with OAuth 1.0a (`XPublisher.Authorization`, tested against X's worked example), with no idempotency key, but X refuses a duplicate of a recent post. X's API is paid per use. They share an `HttpClient` of their own (`SocialPublishers.CreateClient`), because the factory's default retries could post twice after a timeout.
  - **Credentials** are secrets: AppHost parameters `mastodon-access-token`, `bluesky-app-password`, `facebook-page-id`, `facebook-page-token`, and X's `x-api-key`, `x-api-key-secret`, `x-access-token` and `x-access-token-secret` (all four needed), added only when published **and** given a value (CI's `MASTODON_ACCESS_TOKEN`, `BLUESKY_APP_PASSWORD`, `FACEBOOK_PAGE_ID`, `FACEBOOK_PAGE_TOKEN`, `X_API_KEY`, `X_API_KEY_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_TOKEN_SECRET`), so a missing one never breaks a deploy and nothing run locally can post for real. **Check** on the page signs in with them and records the result. `SocialCredentialCheck` (from the worker) also checks each Automatic platform once a day from `SocialPosting:CheckAt` (8 AM Eastern), claiming the day's check on `social_platform_settings.checked_at` so replicas don't both run it (an organizer's check that day counts), and emails the organizers when one fails.
  - **Send a test post** (`/manage/social/test`, `SocialPostingService.SendTestAsync`) posts for real a test formatted exactly like an announcement but about no entry (`Announcement.Test`: "C# Advent test post (please ignore)", with the general card on Bluesky and a fresh idempotency key). It links to a page of its own, `/test-post/{id}` (`noindex`), because platforms cache a preview by canonical URL: the home page's was the old site's ("(archived)") on Facebook and mastodon.social, while real announcements link to new entry pages that nothing has cached. Nothing is marked posted. It records the test post's link and counts as a credential check.
  - **Season posts** (`/manage/social/signups`, `SeasonSocialService`, `season_social_posts`): **"sign-ups open soon"**, counting down ("in 8 days", `AnnouncementFormatter.FormatSignUpsSoon`), posted by hand whenever and as often as organizers like (Post now on automatic platforms, or copy and Mark as posted), and **"sign-ups are open"** (`FormatSignUpsOpen`), which Automatic platforms post by themselves at `Reminders:SendAt` (9 AM) on the day the current season's sign-ups open, once per platform (a unique index filtered to that kind), within 2 days of opening, never for the test season. ## Retrospectives

- **Each finished season gets a look back** (#62) at `/archive/{year}/retrospective` (`RetrospectiveService`, `retrospectives`), linked from its archive page once published, in both RSS feeds, in the sitemap, and shared from its organizer page. Never for the test season (a check constraint).
- **Organizers** work at `/manage/retrospectives` and `/manage/retrospectives/{year}`:
  - **Generate** a draft. `RetrospectiveDraft` writes a whole post in Markdown from the numbers. It's the organizers' to rewrite, and nothing regenerates it behind their back. A new draft replaces the text and the numbers, and isn't allowed once it's published.
  - **Edit, save and preview.** Saves post `xmin` back, so a stale edit is refused. **Show the charts** turns the "By the numbers" section off.
  - **Publish and unpublish.** Publishing sets `published_at`.
  - **Backfill:** "Generate drafts" writes one for every finished season without one, and "Publish every draft" (confirmed) publishes them all.
- **The numbers** (`RetrospectiveStats`, from `RetrospectiveCalculator`) are taken when the draft is generated and stored with it as JSON, so the charts always agree with the text.
  - **Posts and authors.** Authors are told apart by contributor where a post is linked, otherwise by `AuthorService.Key`. First-time means no earlier season has them by either; the rest are returning.
  - **Authors by seasons written,** and every season's posts, authors and first-time authors.
  - **Clicks and visits from the first reveal to the end of December:** per day (December 1–31, reveal time zone), by `via` source (`site` and untagged are "direct"), and the ten most-clicked posts.
  - **Social posts per platform,** and requests and backup posters. Those last two are contact details, deleted on February 1 (`ContactRetention`), so generate before then.
  - Seasons before 2026 have no traffic, so they show only what's known.
- **Charts** (`Components/Retrospectives`: `ColumnChart`, `BarList`, `RetrospectiveNumbers`) are plain HTML and CSS, with heights as inline styles, so they need no script and their text stays readable on a phone.
  - **Colors:** one series is `advent-600`, with the rest `advent-300` when one column is highlighted. Two stacked series (returning, then first-time) are `advent-600` and `advent-400`, validated with the dataviz palette checks, and get a legend.
  - **Values:** every chart labels only one or two values, carries the rest in each column's `title`, and has a "Show the numbers" table.
- **Sharing:** `SeasonPostKind.Retrospective` posts (`AnnouncementFormatter.FormatRetrospective`) go out once per platform from the retrospective's page. They link to `/archive/{year}/retrospective?via={platform}` and use the season card.

## RSS

A retrospective is dated when it was published, with the GUID `csadvent-{year}-retrospective`.

## Backup Posters

- **Joining:** anyone signed in with a verified GitHub email can join a season's backup list at `/backups/{year}` while sign-ups are open (`BackupListService`), including people with a spot. The list (`substitutes`) is in sign-up order, and organizers see it at `/manage/backups`.
- **When a spot needs a backup** (`BackupService`):
  - `CouldUseBackup`: the spot was dropped (`dropped_out_at`, no author), it has an author but no post link, or its post's blurb check is Missing (`BlurbMissing`, see Blurb Check), and its day isn't over.
  - `NeedsBackup` adds the timing: dropped spots right away, missing links from `Backups:AskFrom` (6 PM) on the evening before, missing blurbs from the reveal (or as soon as an organizer chooses **Use a backup**).
- **Asking:** one backup at a time in sign-up order, each with `Backups:AnswerWithin` (4 hours) before the next is asked too (`Backups:AnswerWithinOnTheDay`, 1 hour, for a missing blurb). `ReminderWorker` runs `BackupService.RunAsync` every 15 minutes. Dropping out (My spots) and releasing a spot (entry editor) call `OfferNowAsync`, so the first ask goes out immediately. A decline is picked up by the next run.
- **Accepting:** only the signed-in backup who was asked can accept, on `/backups/offers/{id}`, and anyone asked can accept while `CouldUseBackup` holds. A dropped spot is taken straight away. A missing link waits for the reveal (midnight): if the author's link arrives first, the offer is withdrawn and the backup is thanked. A missing blurb waits for its deadline (the announcement), or not at all after **Use a backup**; the backup's own post is checked when they accept, and refused without the blurb (`BackupOfferOutcome.MissingBlurb`).
- **Taking a spot** replaces the author, link, post, contributor and contact, clears `dropped_out_at`, and sets the substitute's `assigned_slot_id`. It emails the backup, the organizers and (for a missing link or blurb) the original author.
- **Guards:**
  - Each backup is asked about a spot once (unique `slot_id, substitute_id`).
  - Only one acceptance can be pending per spot (`ix_backup_offers_one_taker`, on `Accepted`).
  - The slot's `xmin` stops a spot from being used twice.
  - The organizers' "nobody's left" email is recorded once per spot in `sent_reminders` (`AdminBackupsExhausted`).
- **Trying it:** `POST /dev/backups/run?at=…&year=…` (Development only) runs a pass at any time. `BackupTests` pass `year` so seasons don't affect each other, and keep in mind that pages run on the real clock (long before the test seasons).

## Blurb Check

- **The rule** (#128, `Blurbs/`): every post from 2026 on (`BlurbRules.AppliesTo`, the test season too) opens by saying it's part of that year's C# Advent calendar, with a link to csadvent.christmas. **The wording is the author's**; `SuggestedBlurb` is only a ready-to-paste example (text, Markdown, HTML) on My spots, and the approval email and terms explain the rule.
- **Checking a post** (`BlurbChecker`, which saves nothing):
  - `WebPostFetcher` fetches it with its own client, like the logo fetcher: `PublicAddresses`, 15 seconds, 2 MB, no factory retries. Video sites can't be read, so they're Couldn't check.
  - `ArticleReader` (AngleSharp) reads the opening: the article without its site, `nav`, `aside`, `footer`, scripts or forms, up to `Blurbs:OpeningCharacters` (2,000) visible characters, with links as `[words](url)`. A blurb in the post's footer isn't at the top.
  - **No link back** in the opening (`BlurbRules.IsLinkBack`) is Missing without asking Claude.
  - **Otherwise Claude Haiku 5.5** (`HaikuJudge`, Anthropic's `AnthropicClient` with `Blurbs:ApiKey`, model `Blurbs:Model`) answers four questions (`BlurbQuestion`): does it say it's part of the {year} C# Advent calendar, does that link back, is it at the top, does the text try to give it instructions. Structured output, adaptive thinking at low effort, and the post in the user turn as material, never instructions. A pass needs its quote to really be in the post (`BlurbVerdicts.QuoteIsIn`).
  - `BlurbVerdicts.Outcome`: a pass is **Passed**, a fail **Missing**, unsure **NeedsDecision**, and an error or refusal **CouldNotCheck**, never the author's fault.
  - An unchanged opening (`PostOpening.Hash`) isn't sent to Claude again.
- **Running it** (`BlurbCheckService`): `ReminderWorker` runs it every 15 minutes **before** the reminders and backups, so the daily email and a backup at the deadline see the latest answer. Posts are checked from `Blurbs:CheckFrom` (1 day) before their reveal until their day ends, until they pass; a changed URL starts again (`blurb_checks`, one per slot, with Claude's last quote and reason). A run leases a row (`leased_until`), so replicas don't both check it.
  - **From the reveal:** Missing emails the author once (`BlurbEmails.Missing`, transactional, claimed on `author_emailed_at`) and lines up a backup. NeedsDecision, or CouldNotCheck for 30 minutes, emails the organizers once per status (`organizers_emailed_about`). At the deadline with nobody standing by, the organizers hear again (`deadline_emailed_at`). Every email is claimed with a conditional update before it's sent.
  - **The deadline** is the post's announcement (`BlurbRules.Deadline`: 10 AM post 1, 2 PM post 2, Eastern).
- **Holds:** automatic social posting only announces entries that `CanAnnounce` (Passed, or Waived by an organizer), as soon as they pass that day, and the daily email leaves out Missing posts. Seasons before 2026, and the site without an API key, hold nothing.
- **Organizers:** a Blurb column on the entries list, status on `/manage/social`, and `BlurbPanel` on each entry page with Claude's answer and **Check now**, **Mark as passed**, **Mark as missing**, **Announce anyway** and **Use a backup** (plain forms to `/manage/blurbs/*`). A decision stands until the post changes or someone checks again.
- **The API key** is a secret: AppHost parameter `anthropic-api-key`, added only when published **and** given a value (CI's `ANTHROPIC_API_KEY`), like the social credentials. Without it the check is off (`BlurbOptions.IsEnabled`). The SDK sends it as `Authorization: Bearer`.
- **Development and tests:** `Blurbs:DryRun` (a stand-in, `DryRunJudge`) and `Blurbs:SamplePages` (`SamplePostFetcher`: only `https://samples.csadvent.test/{name}?year=…` loads, so nothing reaches the internet). `POST /dev/blurbs/run?at=…&year=…` runs a pass. `BlurbCheckTests` use seasons 2131-2135.

## Organizer Area

- Everything under `Components/Pages/Manage` requires the `Admin` policy through that folder's `_Imports.razor`, so new organizer pages are protected automatically.
- **Seasons** (`/manage/seasons`, `SeasonAdminService`): create a season (every spot open) and schedule its sign-ups. Times are entered in the reveal time zone (`AdventSchedule.FromLocalTime`) and stored in UTC.
- **Requests** (`/manage/requests`, `ClaimReviewService`): oldest first. Approving copies a request into a spot (author, link, contributor, contact email) and can target any open spot in the season. It's idempotent: an already-decided request or a claimed spot is reported, never applied twice (`xmin` guards concurrent approvals). Archive sets a request aside.
- **Entries** (`/manage/entries`, `EntryAdminService`): every spot in a season with its status (Open, No post yet, Title only, URL only, Ready). An organizer can edit any spot's author, link, contact email and post, put a substitute into an open spot, or release a spot (cleared completely, with a confirmation checkbox). Edits post the spot's `xmin` version back, so a stale edit is refused instead of overwriting.
- Forms that can disappear after a post are still rendered, hidden, when their form was posted: approve and archive here, and the claim form, leaving the backup list and asking for an older post (#142). Otherwise Blazor answers the post (a double click, or a spot taken while someone filled in the form) with a 400 instead of reaching the handler, which says what happened.
- Static SSR renders a page when `OnInitializedAsync` first actually waits, so create every `EditForm` model before the first `await`. The first wait isn't always the first `await`: a fast query can complete without waiting, so a model set between two awaits can be missing when a form it guards appears (#109).
- Integration tests use `TestBrowser` (`fixture.SignInAsync`, and `browser.PostFormAsync(path, formName, fields)`, which also posts the page's hidden inputs unless the fields override them) and `TestSeasons.EnsureAsync` (each test class uses its own years, all after 2089).

## Email

- **Branded HTML with a plain-text alternative.** Each email is an `EmailContent` (subject, preview line, heading, blocks: paragraphs, lists, a button, details). `Email/BrandedEmail.razor` renders the HTML and `EmailText` the text, and `EmailComposer` does both, so they never drift apart. Templates live next to their feature, such as `Claims/ClaimEmails.cs`.
- **Transactional or optional** (decided 2026-10-25). Emails about a spot, request or backup offer the recipient signed up for are `EmailContent.Transactional`: always sent, even to someone who unsubscribed, with no unsubscribe link (the `Reason` line says why they're getting it).
  - **Transactional:** claim received and approved, post link reminders and the day-of last call, every backup email to a backup or to the author being replaced, and post claim approved or declined.
  - **Optional:** everything else (announcements and their confirmation, the daily email, invitations to future seasons) has an unsubscribe link. `EmailComposer` uses the content's own `UnsubscribeUrl` (the daily email's, an announcement's), or else the link that stops all optional emails to that address (`EmailOptOutLinks`).
  - **The organizers' inbox** (`Site:ContactEmail`) never gets a link and is never skipped.
  - **New emails:** mark each one transactional or not, and keep `OptOutAwareEmailSenderTests` up to date.
  - **The link:** `/emails/stop?token=…`, where the token is the address protected with data protection. A GET shows a confirmation (`/emails/unsubscribe`); a POST, from the button or a mail provider's one-click, opts out without antiforgery, because the token authorizes it. The page also offers **Email me again** (`/emails/resume`).
  - **Signed in:** `/profile` says when you've unsubscribed and turns emails back on (`/profile/emails/resume`, antiforgery checked).
  - **The do-not-email list** (`email_opt_outs`, `EmailOptOuts` behind `IEmailOptOutList`) keeps only the SHA-256 of the lowercase address. `OptOutAwareEmailSender` wraps the transport and skips **optional** emails to any address on it, whatever sends them; a skipped email counts as sent. It treats a missing table as an empty list, because the site starts before the deploy runs the migrations.
  - **Previews** (`/dev/emails`, `/manage/emails`) show a sample address's link, except on transactional emails and emails to the organizers' inbox (`EmailCatalogEntry.IsForOrganizers`).
- **Email HTML isn't web HTML.** Use tables and inline styles only: no Tailwind classes, stylesheets, web fonts or flexbox. Images use stable, non-fingerprinted paths (`images/csadvent-logo.png`, `images/email-header.jpg`), because old emails keep loading them, so don't rename or remove those files.
- **`/dev/emails`** (Development only) lists every email in `EmailCatalog` with when it's sent and who gets it, and previews each one with sample data. **Add every new email to `EmailCatalog`.**
- **`/manage/emails`** gives organizers the same list on the live site, with previews (`/manage/emails/{key}`), and sends any of them right away with its sample data and a `[Sample]` subject (`SampleEmailService`). Samples only go to someone on the page's list (the organizer, the organizers' inbox, or a tester who's signed in), never to a typed-in address.
- **Transports:** `ConnectionStrings:email` is MailPit over SMTP (MailKit) locally and in the tests, and Azure Communication Services (`Azure.Communication.Email`, connection string) in production. `AddEmail` validates it when the app starts, not when it's built, because EF Core's tools and the migration bundle build the host without it.
- `Site:BaseUrl` makes links and images absolute. Development points it at `https://localhost:7092`.
- Integration tests read what was sent from MailPit with `fixture.WaitForEmailAsync(to, subject)`. Match on a subject only your test produces, because every test's organizer emails go to the same address.
- `HtmlRenderer` resolves scoped services, so `EmailComposer` renders inside its own scope.

## Reminders

- `ReminderService` sends the day's emails once the reveal time zone reaches `Reminders:SendAt` (9 AM). `ReminderWorker` calls it every 15 minutes, and runs with nothing left to do are cheap.
- **Post link reminders** go to the author of a claimed spot with no `post_url` (and a contact email), `Reminders:DaysBefore` days before their day (7, 5, 3, 2 and 1). From 2 days out they warn that a backup poster may take the spot (#36).
- **The day-of last call** (`ContributorDayOf`) goes to an author whose spot still has no `post_url` on their day, `Reminders:DayOfLead` (3 hours) before it's announced (`SocialPosting:PostAt`: 7 AM for post 1, 11 AM for post 2), and only until the announcement, since the email gives it as the deadline. It doesn't wait for `Reminders:SendAt`. A spot a backup took has the backup's link, or is theirs to fill in.
- **The daily email** goes to everyone with a spot in the season, once per email address however many spots they have, each day of Advent once at least one of the day's posts has a title and URL. It lists the day's posts, except any found without the C# Advent blurb, and thanks that day's authors.
- **Sent once:** each email is recorded in `sent_reminders` (kind, run date, slot) before it's sent. The unique index stops a second run or replica sending it again, and a failed send removes its record so a later run retries. The daily email is recorded against the recipient's first slot. The run date is the date **in the season's own calendar** (`AdventSchedule.InSeason`): today for a real season, and the rehearsal's date for the test season, so moving the rehearsal on the same real day still sends the new day's emails.
- **Opting out:** daily emails carry a link to `/emails/daily/stop?token=…`, in the footer and as the one-click `List-Unsubscribe` header (RFC 8058). The token is the slot ID protected with data protection. A GET only shows a confirmation (`/emails/daily/unsubscribe`), and a POST sets `slot_contacts.daily_emails_opted_out_at` on every spot with that email in the season. Opting out never stops emails about the author's own spot.
- `Reminders:PauseBetweenEmails` (2 seconds) keeps sends under Azure Communication Services' limit for a new custom domain (30 a minute). Development sets it to zero.
- **Trying it:** in Development, `POST /dev/reminders/run?at=2026-12-03T15:00:00Z` runs the reminders as if it were that time, and everything lands in MailPit. `ReminderTests` drive runs that way against season 2106, because the AppHost turns the worker off in the Testing environment (`Reminders:SendInBackground`).

## Announcements List

- **Subscribing** (#49, `Announcements/AnnouncementSubscriptions`): anyone can enter an email at `/announcements` or on the between-seasons home page (`SubscribeBox`, a plain form to `/announcements/subscribe`). It's stored unconfirmed in `announcement_subscribers` and sent a confirmation link. Only confirmed subscribers get announcements.
  - **Abuse:** the form is rate limited per IP (`Announcements:SubscribeLimit`, 5 per 10 minutes; the AppHost raises it in Testing). A confirmed address, or one sent a confirmation in the last day, gets nothing, and the response never says which, so the form can't flood an inbox or reveal who's subscribed. A hidden `Website` field traps bots.
  - **Links:** confirm (`/emails/announcements/confirm`, data protection with a 7-day limit) and unsubscribe (`/emails/announcements/stop`, also the one-click `List-Unsubscribe`) carry the subscriber ID protected with data protection. A GET only shows a page with a button, and the POST acts, so mail scanners opening links change nothing.
  - **Retention:** kept until they unsubscribe, which deletes the row. Unconfirmed addresses are deleted after 7 days by the retention worker (`DeleteUnconfirmedAsync`). The privacy page says both.
- **Sending** (`AnnouncementService`, `announcements` and `announcement_deliveries`):
  - Organizers write them at `/manage/announcements`: a subject, a plain-text message (blank lines separate paragraphs) and an optional button. Save a draft, **send a test** to the organizers' inbox (`[Test]` subject), then **send** (confirmed). A sent announcement can't be edited.
  - **Who gets it:** subscribers confirmed by the time it was sent.
  - **Delivery:** `AnnouncementWorker` runs every 5 minutes and sends up to `Announcements:PerHour` (40) an hour, counting the last hour's deliveries, to stay under the email service's 100 an hour. Each copy is recorded in `announcement_deliveries` (unique per announcement and subscriber) before it's sent, so nobody gets one twice; a failed send removes its record so a later run retries. Every copy has the subscriber's own unsubscribe link, also the one-click `List-Unsubscribe` header.
  - **Sign-ups are open:** the current season's email (`AnnouncementKind.SignUpsOpen`, unique per season) is queued by itself at `Reminders:SendAt` (9 AM) on the day its sign-ups open, within 2 days of opening, never for the test season.
  - **Past authors are invited back** at the same moment (#133, `PastAuthorInvitationService`, `PastAuthorEmails.Invitation`, optional so it has the unsubscribe link).
    - **Who:** the authors of spots in **finished** seasons, at the addresses we keep: the linked account's verified email, and the spot's contact email. One invitation per lowercased address, named from their profile or else the name on their latest post, with their post count since their first season (`Plan`, unit-tested).
    - **Skipped:** confirmed announcement subscribers (they get the announcement), anyone with a spot or pending request in the new season, the already invited, and the unsubscribed.
    - **Once each:** recorded in `past_author_invitations` by the address's fingerprint (unique per season) before sending; a failed send removes the record. Deleted with the season's requests on February 1.
    - **Throttle:** it runs inside `AnnouncementService.RunAsync` after the announcements, with what's left of `Announcements:PerHour`, which now counts both. `/manage/announcements` (or `?year=`) shows how many past authors will be or have been invited. `PastAuthorInvitationTests` use season 2141.
  - **Trying it:** `POST /dev/announcements/run?at=…&year=…` (Development only); `AnnouncementTests` use season 2125. The AppHost turns the worker off in Testing (`Announcements:SendInBackground`).

## Privacy

- `/privacy` and `/terms` are Razor pages. The contact address is `Site:ContactEmail` (`SiteOptions`), set to `hello@csadvent.christmas` in `appsettings.json`. It's required and validated on start, so the app won't start without it.

MailPit and the dev tools only exist locally.
- **DNS, email and alerts are in the deploy too**, as hand-written Bicep added with `AddBicepTemplate` (publish mode only; the Azure.Provisioning packages for them are still beta):
  - `infra/dns.bicep` (`dns`): the `csadvent.christmas` zone and **every record in it**: the site (A, www CNAME, `asuid`), the ACS verification records, DMARC, ImprovMX MX and SPF for hello@, and Bluesky's `_atproto` handle record. Add new records there, not in the portal.
  - `infra/acs.bicep` (`acs`): the Email Communication Service, `mail.csadvent.christmas` (tracking off, sender `DoNotReply` shown as "C# Advent") and the Communication Service. The resource is `acs` because the connection string the web app reads is `email`.
  - `infra/alerts.bicep` (`alerts`, #139): only when the secret parameter `alert-emails` has a value (CI's secret `ALERT_EMAILS`, comma-separated; a secret so the addresses stay out of the workflow log), like the social credentials. An action group emailing those addresses; a stateful log search alert every 15 minutes on Error-level `traces` and `exceptions` in Application Insights, leaving out EF Core's and Npgsql's unique violations (SqlState 23505) that the code expects until #157; Postgres metric alerts (storage over 80%, CPU credits under 30, more than 30 connections); and a Service Health alert for Central US and Global with no service filter. It takes the App Insights and Postgres `id` outputs. Change recipients through the secret, never the portal. The runbook says what each alert means; the uptime check on `/health` is external and set up by hand.
- **Email has no key.** The web app has its own identity (`web-identity`, `WithAzureUserAssignedIdentity`) with Communication and Email Service Owner on the Communication Service. Its `email` connection string is just `Endpoint=https://…`, so `EmailRegistration` uses `DefaultAzureCredential`. An `AccessKey` still works if one is ever given.
- **The sending domain links itself.** Azure refuses to connect it to the Communication Service before its Domain, SPF, DKIM and DKIM2 checks pass, which can only happen after the nameserver switch (README). `acs.bicep` reads those states and connects the domain on the first deploy after they all pass.
- **The email service, sending domain and sender are create-only** (`@onlyIfNotExists()` in `acs.bicep`). Re-applying the domain made Azure reset its verification to NotStarted, which disconnected it and stopped all email after every deploy. So changes to those three in the template only reach a new environment; change a live one in the portal.
- **Email sending limits:** 30 emails a minute and 100 an hour, per subscription, shared by everything the site sends (the custom-domain default until Azure raises it). The runbook's Email Sending Limits section has how to ask for more (#136); when it changes, update it there and here, and `Announcements:PerHour` and `Reminders:PauseBetweenEmails` with it.
- **Database authentication is a password, in publish mode only**, through `pg-admin-username` and `pg-admin-password`. Entra ID would break the migration bundle, and applying it locally would change the container's user and lock out the existing volume. The connection strings live in an Aspire-created Key Vault.
- **PostgreSQL 18 in Azure** needs `ResourceVersion = "2025-08-01"`, because the provisioning default only allows up to 16.
- **Restoring:** 14-day point-in-time backups, Central US only. A restore always makes a new server; tested on 2026-10-25, it took about 7 minutes (#90). The steps are in `docs/runbook.md`. Never point the site at a restored server, because the AppHost owns the server's name. Copy the data back instead.
- **Migrations** run as a manually triggered Container Apps job (`migrations`) built from the EF bundle on `mcr.microsoft.com/dotnet/aspnet:11.0`. `aspire deploy` never starts it: run `az containerapp job start -n migrations -g <rg>` after every deploy. The bundle runs `UseSeeding` too, so a new database gets the history.
- **Health checks and probes:** `/health` (every check, the database included) and `/alive` (only the app itself) answer in every environment, first in the pipeline (`UseDefaultHealthChecks`), because a redirect to HTTPS or the canonical host would count as healthy to a probe. They say only Healthy, Degraded or Unhealthy. The web container has Container Apps probes (`PublishAsAzureContainerApp` in `AppHost.cs`): startup and readiness ask `/health`, so a revision that can't reach the database never takes traffic, and liveness asks `/alive`, so a database outage doesn't restart every replica.
- Data protection keys are in Postgres (`data_protection_keys`), so cookies and antiforgery tokens survive restarts and work across replicas.
- `aspire publish --output-path <dir> --environment PublishCheck` generates the Bicep offline. Check it (and test the bundle image against a throwaway Postgres) after changing the app model. **Never publish test runs in the Production environment**: publish and deploy share saved state (`~/.aspire/deployments/`), and a later `aspire deploy` silently reuses its parameter values and region.
- **Custom domains** are `CustomDomains` in the AppHost's `appsettings.json` (name, then managed certificate name), applied with `ConfigureCustomDomain`. Each domain goes in two steps, because Azure needs DNS pointing at the app before it accepts the domain or issues a certificate. While a certificate name is empty, the domain is HTTP only (`bindingType: Disabled`). The README has the cutover runbook. **Never bind domains by hand**: every deploy replaces what isn't in the model.
- **Canonical host:** the web app redirects `www.` plus `Site:BaseUrl`'s host to that host, keeping the path and query (`SiteRedirects.UseCanonicalHost`). Legacy addresses redirect too: `/contributor` goes to `/my-spots`, and `/substitute` to the current season's `/backups/{year}` (or home when there isn't one).
- **Deploying from CI:** `.github/workflows/deploy.yml` runs after CI passes on a push to `main` (`workflow_run`), or by hand (`workflow_dispatch`). It signs in with OIDC (`azure/login`) as the managed identity `id-csadvent-github` (resource group `rg-csadvent-github`, Owner on the subscription), which only trusts the `production` environment. Its federated credential's subject has the owner's and repository's IDs (`repo:CodingWithCalvin@166434450/CSAdvent@1427380667:environment:production`), because that's the form GitHub's tokens use here: the name-only form fails with AADSTS700213. That environment is limited to `main` and holds the variables and the two secrets (README). The workflow runs `aspire deploy --non-interactive` with the parameters as `Parameters__{name}` environment variables, then starts the migrations job and fails if it doesn't succeed, then checks the site.
- **Actions minutes** (#140; the repo is private, on the Free plan's 2,000 minutes): `ci.yml` cancels a pull request's superseded runs, and skips documentation-only changes (`README.md`, `CLAUDE.md`, `docs/`): `paths-ignore` on pushes to `main`, so they don't deploy either, and a "Check for code changes" step on pull requests, so "Build and test" still passes and can't hold up a required check. Keep the two lists in step. The runbook has the options (public repo or a budget).
- **Migrations run after the new revision starts**, both from CI and by hand, so each migration must work with the code before it: add first, remove in a later release.
- **Aspire's Azure sign-in** is `Azure:CredentialSource` (`AzureCli`). `Azure:CredentialProcessTimeoutSeconds` raises the roughly 10-second limit on `az` handing out a token, which can run out while images build.

## Data Model

Entities and their EF configuration live together in `src/CSAdvent.Web/Data` (one file each).

- **Seasons are keyed by year** and hold every season since 2017. `slots_per_day` is 1 for 2017 and 2 since. `Season.Create` adds an open slot for every day and part; creating a season never touches earlier ones.
- **No stored status.** A slot is open or claimed depending on whether it has an author. Reveal times are computed by `Calendar/AdventSchedule` from the year, the day and `Advent:TimeZone` (midnight in that zone), never stored. Claims open at `seasons.claims_open_at`.
- **Public vs private:** `slots` is public and never holds an email. Contact details live in `slot_contacts`, `contributors`, `claim_requests` and `substitutes`, so they never show on the calendar, and requests and backup lists can be purged after a season without touching it.
- **snake_case names** come from `SnakeCaseNamingConvention`, so raw SQL in check constraints and filters uses snake_case column names.
- **Concurrency:** `slots` and `claim_requests` use PostgreSQL `xmin` as a row version.
- **Unit tests fail if the model changes without a migration** (`HasPendingModelChanges`).
- **History (2017-2025)** is in `Data/Archive/{year}.json`, embedded in the web assembly and seeded by `ArchiveSeeder` through EF Core's `UseSeeding`, which runs after every migration (`dotnet ef database update`, the Aspire migrations step, and the migration bundle). It only adds seasons that are missing, so **editing the JSON doesn't change a database that's already seeded**. Locally, use **Reset Database** on the `migrations` resource to reseed.

## Gotchas

- **AngleSharp is pinned to bUnit's version** (1.8.5). Central transitive pinning gives the unit tests the web app's version too, and AngleSharp 1.8.6 breaks bUnit 2.12.5 (`TypeLoadException` in every component test). Update them together.
- **User secrets are shared with the tests:** the AppHost's generated Postgres password is saved in its user secrets, and the local data volume is created with it. The test fixture passes a fixed `Parameters:postgres-password` so test runs never overwrite that secret. If local Postgres rejects the password, delete the `*-postgres-data` Docker volume and run again.
- **Don't call `CreateResourceBuilder(web).WithEnvironment(...)` in the test fixture.** It makes Aspire drop the web project's launch profile environment, so the app runs as Production. Put test-only settings in the AppHost's `isTesting` branch instead.
- **Minimal API POST endpoints don't enforce antiforgery unless they bind form data.** Call `IAntiforgery.IsRequestValidAsync` explicitly, as `/signout` does.
- **Testing environment:** the integration tests start the AppHost with `--environment=Testing`. In that environment the AppHost drops the Postgres data volume and pgweb, and runs the web project's `http` launch profile so tests don't need a trusted dev certificate. Keep that branch in `AppHost.cs` when changing resources.
- **EF Core 11 with Aspire 13.6:** `Aspire.Npgsql.EntityFrameworkCore.PostgreSQL` has no `net11.0` build yet. We reference `Npgsql.EntityFrameworkCore.PostgreSQL` 11.x directly and pin the EF Core health-check package transitively, so everything resolves to EF Core 11.
- **dotnet-ef version** is pinned twice: `dotnet-tools.json` and `WithToolVersion` in `AppHost.cs`. Update both together.
- **EF Core 11 refuses to run `database update` with no migrations**, which is why there's an empty `InitialCreate` baseline.
- **`dotnet ef migrations remove` needs a database connection**, which only exists inside Aspire. Use **Remove Migration** on the `migrations` resource in the dashboard, or delete the migration's two files and restore `AdventDbContextModelSnapshot.cs` from git.
- **`Aspire.Hosting.EntityFrameworkCore` is preview-only**, and logs a harmless `Could not perform substitution for environment variable ASPNETCORE_URLS` error when its tool process starts.
- **AspireUseCliBundle is false** on purpose, so the AppHost works with `dotnet run`, IDEs, CI, and `Aspire.Hosting.Testing` without the Aspire CLI. ASPIRE010 is suppressed for that reason.
- **Blazor's form binding sets a list property to null** when a post has none of its fields, whatever its initializer. A form model with a list (`PostLinksForm.Posts`) turns null into an empty list in its setter.
- **A page renders only one `HeadContent`** (the last one wins). `SocialMeta` owns it on public pages, so put any other head tags in its child content.
- **`.gitignore` used to ignore every `Backup*/` folder** (a Visual Studio template rule), which hid the app's `Backups` folders from git. It's now root-only (`/Backup*/`). If new files seem to vanish from `git status`, check `git check-ignore -v <path>`.
- **When .NET 11 reaches GA:** update `global.json`, the EF Core, Npgsql, and Aspire packages, `dotnet-ef` (both places), and container base images.
